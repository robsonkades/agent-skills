Use when a design is starting and the patterns are about to be chosen\n  by habit, when a pattern name is proposed before the problem is stated, when two chosen\n  patterns produce friction, when a reference architecture is being copied wholesale, when\n  someone asks which enterprise patterns a new module should use, or when an architecture\n  must be explained as a set of decisions. Does not cover the individual patterns' guidance,\n  whether the framework provides one (patterns-and-modern-frameworks), or detecting overuse\n  (enterprise-architecture-smells).\n---\n\n# Pattern Selection and Composition\n\n## Purpose\n\nDerive an architecture from forces, and check that its parts fit. Patterns are the _output_\nof reasoning about a problem, never the input — \"we will use a domain model with\nrepositories and DTOs\" stated before the forces are known is a preference, and it will be\ndefended rather than tested.\n\nThe second half matters as much: patterns interact. Some pairs reinforce each other (Domain\nModel with Unit of Work and Identity Map); some fight (Domain Model with a repository that\nreturns rows on its invariant-enforcing write path; a facade that leaves remote calls chatty). A design of individually\ndefensible choices can still be incoherent.\n\n## The selection inputs\n\n```text\nBusiness complexity      do the rules interact? how many are conditional\n                         on other rules?\nData complexity          does the object model diverge from the schema?\n                         who owns the schema?\nWork shape               per-instance decisions, or set-shaped work?\nConcurrency              conflicts within a transaction, or across a\n                         user's thinking time? which reads/writes share an invariant?\nTransaction scope        one write, several writes, or across a boundary?\nDistribution             one process, or several? whose driver?\nPerformance              round-trip budget; read/write asymmetry\nTeam and lifespan        who maintains it, for how long, at what size\nOperational constraints  deploy cadence, ownership, regulatory limits\n```\n\nEverything below is derived from these. If a pattern cannot be traced back to one of them,\nit has no justification yet.\n\n## Workflow\n\n1. **Inspect evidence for the relevant inputs** for the module — not just the system.\n   Reuse accepted constraints and existing code. Record consequential unknowns and investigate\n   the smallest missing basis; do not require nine new answers for a small decision. Retain\n   an adequate composition when no unmet requirement or observed cost justifies changing it.\n2. **Start with logic organisation, then iterate with fixed schema, transaction, concurrency and\n   delivery constraints.** It constrains many downstream choices but is not a one-way dependency\n   (`domain-logic-organization`).\n3. **Choose the data-source pattern** consistent with it (`data-source-patterns`).\n4. **Add only the patterns a named force requires.** Each addition must trace to an input.\n5. **Check the composition** against the conflicts list in the references. Fix the friction\n   by removing unjustified machinery or correcting boundaries. An adapter is justified when\n   independently owned contracts must coexist; measure its cost instead of forbidding it.\n6. **Write down the choices with their forces**, so the next person can re-open a decision\n   on evidence (`architecture-decision-making`).\n\n## Selection rules\n\nThese are candidates to compare with the existing design, not mandatory stacks. Schema\nownership does not alone require duplicate object models; use explicit mapping when the\nsemantic/API independence gained justifies conversion and synchronization costs.\n\n```text\nRules do not interact; work is per-transaction\n        → Transaction Script + Table Data Gateway.\n          Add a Service Layer when transaction, authorization, orchestration or a stable use-case\n          boundary earns it—not from a write-count threshold.\n\nRules interact; invariants span objects; schema is yours\n        → Domain Model (entities with behaviour) + Data Mapper (JPA) +\n          Repository per aggregate + Service Layer for the transaction.\n\nRules interact; schema is owned elsewhere or must diverge\n        → Domain Model + separate persistence model + explicit Mapper.\n          Pay the mapping; you are buying independence.\n\nMostly CRUD; entity ≈ table; you own the schema\n        → consider Active Record where the record owns persistence, or a\n          simple mapper/repository-backed CRUD design already supported by the stack.\n          Add service/DTO boundaries only for a named contract or policy.\n\nWork is set-shaped (bulk recalculation, indexation, reporting)\n        → SQL in a gateway, beside whatever the write side uses.\n          Not a domain model looping over objects.\n\nReads are slow because they go through the write model\n        → inspect query/fetch shape, then consider a read projection or query object\n          when it addresses the measured cost without losing access-control or freshness guarantees.\n\nConcurrent edits across a user's thinking time\n        → compare optimistic validation with pessimistic checkout using conflict frequency,\n          lost-work and waiting/recovery cost. Coordination scope follows the invariant;\n          preserve an adequate existing protocol (offline-concurrency-control).\n\nA remote boundary exists\n        → define coarse-enough operations and an explicit wire contract.\n          A dedicated DTO is usual; a stable schema-generated or immutable\n          boundary type can already satisfy that role.\n\nA remote boundary is being CONSIDERED\n        → module boundary first; distribute only for a named driver\n          (distribution-boundaries).\n\nMulti-request conversation state\n        → place it per item (session-state-strategies), not as a\n          session by default.\n```\n\n## Composition rules\n\n- **ORM-backed Domain Models commonly use Unit of Work and Identity Map.** A domain model\n  alone implies neither; explicit SQL, immutable models and event persistence can differ.\n  Inspect actual persistence semantics rather than inventing ORM behavior\n  (`orm-behavioral-patterns`).\n- **Repository provides collection-like access to domain objects.** When adopting DDD\n  aggregates, organize domain repositories around aggregate roots and protect their mutation\n  boundaries; absence of aggregates alone does not make a Repository a DAO (`repository-pattern`).\n- **Remote Facade needs an explicit wire contract and suitable operation granularity.**\n  A dedicated DTO, schema-generated type or an already stable boundary type can fill that\n  role. Inspect exposed state and coupling before adding copies; one client interaction\n  need not mean one internal network hop (`remote-facade-and-dto`).\n- **Optimistic Offline Lock needs authoritative atomic validation of the expected state\n  and a meaningful conflict outcome.** A version column is common; an original-value\n  predicate or another adequate revision contract can also work. Every relevant writer\n  must participate, including bulk and external writes.\n- **Service Layer defines an application operation boundary.** Transaction ownership,\n  authorization, orchestration and multiple callers can justify it; read-only or remote\n  operations need not start a database transaction\n  (`service-layer-design`).\n- **Atomic commit and per-entity version checks do not by themselves protect every invariant.**\n  If a decision reads several aggregates or a predicate but updates only one, disjoint writers\n  may each pass their local checks while jointly breaking the rule. Identify the invariant's\n  read/write set and authoritative coordination before choosing aggregate boundaries, lock\n  scope or isolation. Preserve a sufficient local protocol when the invariant is local;\n  do not prescribe a larger aggregate or stronger isolation solely from the pattern name.\n- **Outbox follows a durable-publication requirement, not a Domain Model requirement.**\n  When business state and publication intent must commit together, compare an outbox with\n  the existing delivery contract. Transaction Scripts can need it too; a local synchronous\n  event alone does not. Include consumer repeat safety in the composition, since an outbox\n  does not make downstream effects exactly once.\n- **Set-based operations need explicit invariant and concurrency handling.** Table Module\n  can own business rules over tabular data; it does not inherently bypass every invariant.\n- Reads and writes may use different patterns when query and invariant forces diverge.\n  Preserve access policy, freshness and consistency on each path; compare their actual\n  costs (`architecture-and-performance`).\n\n## Conflicts to check for\n\n```text\nDomain Model + repositories returning rows/DTOs\n        → check write paths for bypassed invariants; separate read projections are compatible.\n\nDDD aggregate + independent write repositories for its child tables\n        → inspect whether child writes bypass root invariants; table-oriented\n          infrastructure alone does not prove the aggregate boundary is broken.\n\nActive Record + a Repository abstraction + DTOs everywhere\n        → inspect whether each wrapper protects an independently required contract.\n          Remove unjustified duplication; boundary DTOs or an adapter are not inherently inconsistent.\n\nTransaction Script + a rich domain model half-built\n        → check for two competing owners of the same rule or bypassed invariants.\n          Scripts and models can coexist when each rule has one logical owner.\n\nRemote Facade + fine-grained service methods behind it\n        → compatible for local calls: aggregating them is the facade's purpose.\n          If calls remain remote, inspect the remaining network hops and latency.\n\nVersion-based aggregate + bulk writes bypassing its conflict protocol\n        → expected-state checks and version invalidation must cover these writers too\n          (offline-concurrency-control).\n\nUninitialized lazy state crossing a boundary\n        → inspect the actual ORM/session and serialization contract: detached access\n          may fail, or an open context may hide queries and expose unintended state.\n\nCoarse-Grained Lock + a large aggregate\n        → measure contention and invariant scope before resizing; splitting an\n          atomic invariant introduces a coordination problem, not a free optimization.\n\nDistribution + a shared database\n        → coupled schema, availability and ownership. This may be a deliberate\n          transitional or jointly owned architecture; it does not by itself prove\n          one service, but it weakens independent evolution.\n```\n\n## References\n\nReturn the selected, retained or rejected composition, the relevant evidence and constraints, its main\ntrade-off, and a concrete validation or reconsideration condition. Do not infer a performance\nimprovement from pattern names; inspect versions and measure the target implementation.\n\n- [Selection criteria](references/selection-criteria.md) — the nine inputs turned into\n  questions with observable answers, worked selections for four common system shapes, and\n  the decisions that should differ per module rather than per system. Read when assembling an\n  architecture or explaining an existing one, especially when a rule spans independently\n  versioned aggregates.\n"

Inspect representative\nchanges and preserve justified existing boundaries.\n\n## Four worked selections\n\n### A. Internal CRUD administration for reference data\n\n```text\nBusiness complexity   2 validations, no interaction\nData complexity       entity = table; we own the schema\nWork shape            per instance\nConcurrency           two admins, rarely the same row\nTransaction scope     one write\nDistribution          none\nPerformance           irrelevant volumes\nTeam                  one team, long-lived, small\n\n→ Simple mapper-backed CRUD (JPA entity plus Spring Data repository is not Active Record)\n→ Existing Spring Data repository API; no extra pass-through wrapper\n→ Service layer only if shared authorization, transaction or caller contracts warrant it\n→ Reuse adequate internal types; explicit response contract at the HTTP boundary\n→ If stale edits must be rejected, preserve expected state and a tested conflict response\n  (@Version is one option; inspect the actual mapping and target)\n```\n\nCheck what the house layers protect before adding or removing them: authorization, validation,\ntesting and ownership may still justify a small boundary. Record the force and trade-off.\n\n### B. Order management with pricing rules\n\n```text\nBusiness complexity   7 pricing rules, 4 conditional; status transitions\nData complexity       order spans 3 tables; we own the schema\nWork shape            per instance for writes; set-shaped for the nightly re-rate\nConcurrency           users edit an order over minutes\nTransaction scope     order + lines + intent to publish OrderPlaced\n                      publication must survive a crash after commit\nDistribution          none today; inventory may be extracted later\nPerformance           list screen shows 25 orders, 6 columns; budget 200 ms\nTeam                  two teams, long-lived\n\n→ Domain Model: Order aggregate with lines; rules on the objects\n→ Data Mapper via JPA (entities are the persistence model, annotated)\n→ One repository for the Order aggregate; none for OrderLine\n→ Service Layer: one use case per operation, transaction demarcated there\n→ Optimistic Offline Lock, coarse-grained on the Order root\n→ READ MODEL: projections for the list and detail screens\n→ Table Module / SQL gateway for the nightly re-rate\n→ Outbox for durable OrderPlaced publication; repeat-safe consumer effects\n→ Module boundary around inventory; no service yet\n```\n\nProjections and explicit SQL are candidates for the query and bulk budgets, not required\nreplacements for an adequate existing path. Without deliberate fetch/bulk planning, the list may produce\nN+1 and the job may hydrate excessive aggregates. Prove the query/load shape, and ensure\nthe SQL path implements the same required pricing invariants and conflict behavior.\n\n### C. Public API over an existing system\n\n```text\nBusiness complexity   low in the API; the logic is in the existing system\nData complexity       legacy schema, owned by another team, will not change\nWork shape            request/response\nConcurrency           external clients retry\nTransaction scope     one call into the existing system\nDistribution          remote by definition\nPerformance           1 round trip per client interaction\nTeam                  API team ≠ the system's team\n\n→ Remote Facade: operations named after client interactions\n→ Explicit wire types and evolution/unknown-field policy matched to the public contract\n→ Anti-corruption layer when legacy semantics need translation; do not invent that mismatch\n→ Gateway per external system, with error translation\n→ Assess retry safety across all effects; idempotency keys/deduplication only where needed\n→ ETag / If-Match when conditional HTTP updates express the required conflict protocol\n→ No domain model in the API layer — it has no rules of its own\n```\n\nThe failure to avoid here is building a domain model in the API tier \"for cleanliness\". It\nwould be a second, weaker copy of rules that live elsewhere.\nAn older or separately owned system need not have incompatible semantics. Preserve an\nadequate translation boundary and wire type. Repeat-safe intended effects may need no key\nstore; non-repeat-safe effects need an authoritative retry/deduplication or reconciliation\ncontract. A method name or a separate cache does not establish that contract (`idempotency`).\n\n### D. Reporting and analytics over a transactional system\n\n```text\nBusiness complexity   in the queries, not in the objects\nWork shape            entirely set-shaped\nConcurrency           read-only\nPerformance           dominates everything\nTeam                  analysts plus one engineer\n\n→ SQL, in gateways, per report\n→ Projections/records as the result types\n→ Avoid unnecessary write-model hydration; retain query repositories and service/policy\n  boundaries when they own authorization, admission, audit or a stable caller contract\n→ Isolate reporting capacity when measured contention warrants it; replica if freshness permits\n```\n\nProjection-oriented SQL can avoid unnecessary hydration. Projection types and a read-only\nlabel do not enforce database privileges or prevent writes through raw SQL.\n\n## Decisions that belong per module, not per system\n\n| Decision                   | Per system                                            | Per module                                        |\n| -------------------------- | ----------------------------------------------------- | ------------------------------------------------- |\n| Logic organisation         | —                                                     | **Yes** — CRUD and pricing are different problems |\n| Data-source pattern        | —                                                     | **Yes**                                           |\n| Service layer existence    | —                                                     | **Yes**                                           |\n| Read model                 | —                                                     | **Yes** — where reads are slow                    |\n| Locking strategy           | —                                                     | **Yes** — per aggregate, by conflict rate         |\n| Error shape                | Govern per public protocol and compatibility contract | Map local failures without breaking that contract |\n| Transaction boundary layer | Govern ownership and propagation conventions          | Demarcate the actual unit required by this path   |\n| Boundary enforcement rules | **Yes**                                               | —                                                 |\n| Logging and correlation    | **Yes**                                               | —                                                 |\n| API contract conventions   | **Yes**                                               | —                                                 |\n\nThe left column records shared contracts; distinct protocols or existing compatibility\nrequirements may need different representations.     "Content": "# Reference Architectures and the Relationship Graph\n\nThese are conceptual compositions, not mandatory stacks or executable configurations.\nSelect the relevant path and preserve an adequate existing owner/contract. Inspect the\ntarget Java, framework, persistence and protocol versions before implementing a mechanism.\nWhere a diagram says response record, an ordinary immutable DTO class can serve the same\nboundary on older Java; [records became a standard feature in Java 16](https://openjdk.org/jeps/395).\n\n## Composition 1 — rich domain, one process\n\nThis variant includes an outbox because asynchronous publication must survive a process\nfailure after commit. Omit that machinery when the required contract is already met or\nevents are only local synchronous calls whose effects share the transaction.\n\n```text\nHTTP request\n  └── Controller                     bind, validate syntax, map\n      └── Application service        TRANSACTION starts; authorisation\n          ├── Repository (aggregate) load whole aggregate\n          │     └── Data Mapper / JPA  Unit of Work + Identity Map + Lazy Load\n          ├── Domain Model             rules and invariants; state transition\n          ├── Repository.save          (usually implicit: dirty checking)\n          └── Outbox row               written with business state in SAME transaction\n                └── Relay             publishes committed rows; may publish again after failure\n                      └── Consumer    repeat-safe effects or authoritative deduplication\n      └── Response record            projection or mapped from the aggregate\n```\n\n**Consequences:** aggregate fetch cost depends on graph size and fetch plan. Repository access\nalone does not enforce rules: mutation paths must invoke domain behavior and coordinate\nconcurrent changes. Bulk work must preserve required invariants and versions. Reuse this\nread path when its graph/cost fits; use projections when it loads unnecessary state.\nAn after-commit callback alone is not a durable outbox: a crash before publish can lose the event.\n\nThe outbox transaction covers business state and publication intent, not broker acceptance\nand consumer effects. If the relay crashes after the broker accepts a message but before\nrecording success, recovery can publish it again. Preserve stable message identity and make\nconsumer effects repeat-safe; when deduplication is needed, coordinate its record atomically\nwith the effects it protects. A consumer's local database record does not atomically cover\nan external payment or other remote effect; use that system's retry/reconciliation contract\n(`idempotency`). Verify both the lost-publication window and duplicate-delivery window;\nthe relay's retry loop alone does not close the latter.\n\n**Where it fails:** unbounded aggregates; rules that leaked into the service; reads forced\nthrough the write model.\n\n### When the invariant spans independently versioned objects\n\nUnit of Work coordinates persistence and per-entity optimistic checks detect conflicts on\nthe revisions actually validated. Their combination is not proof that a predicate across\naggregates is protected. Consider two on-call staff rows and the rule \"at least one remains\non call\". Each transaction counts two staff on call, then switches only its own row off using\nthat row's expected version. Under snapshot isolation without shared predicate validation,\nboth disjoint updates can commit: both local versions were valid, but no staff remain on call.\n\nIf each row instead has only independent local rules, adequate per-row validation may be enough.\nFor the shared rule, compare a database-enforced constraint when it can express the invariant,\nauthoritative shared validation/locking in which every writer participates, or a serializable\nunit with supported retry handling. The database/provider and the timing of reads and validation\nmatter. Do not simply move both rows into one object, add an annotation, or retry the last SQL\nstatement and declare the composition correct. Retrying must re-evaluate the decision from fresh\nstate and account for effects outside the transaction. If temporary violation is acceptable,\nstate that weaker business contract and its recovery obligation instead of silently assuming it.\n\nPass the invariant, read/write set, writer paths, engine/isolation level and retry/effect contract\nto `enterprise-transactions` for the concrete coordination design. Verify a schedule where both\ntransactions decide before either commits, including bulk/external writers. If that specialist\nor target-engine verification is unavailable, keep the guarantee conditional and state the\ndiscriminating test; a green sequential test does not prove this composition safe.\n\n## Composition 2 — transaction script\n\n```text\nHTTP request\n  └── Controller\n      └── Transaction Script         TRANSACTION; steps; the rules are here\n          └── Table Data Gateway     SQL per table; rows in, rows out\n              └── Database\n```\n\n**Consequences:** fewest moving parts; the SQL is visible and tunable; no ORM behaviour to\nreason about; and duplication is the failure mode — the same rule in several scripts,\ndiverging.\n\nDurable event publication can add the same outbox/relay/consumer composition described above\nwithout changing the logic organisation into a Domain Model.\n\n**Where it fails:** when interacting rules become hard to maintain. The signal is semantic:\nthe same decision duplicated with divergent behavior or costly coordinated edits,\nnot simply a business term appearing in three files.\n\n## Composition 3 — remote API over an application\n\n```text\nClient\n  └── Remote Facade                  one coarse operation per interaction\n      ├── DTO in                     validated; explicit version/unknown-field policy\n      ├── Retry contract             repeat-safe effects or authoritative deduplication\n      ├── Application service        orchestration; transaction where required\n      │     └── Domain / scripts\n      └── DTO out                    materialize required state before its context closes\n```\n\n**Consequences:** fewer required client round trips; the wire contract can evolve\nseparately from the model. Safe retries require atomic deduplication relative to effects,\nstable operation identity and defined replay/retention when effects are not already repeat-safe;\na key and separate cache alone are\ninsufficient, especially when the existing system is remote. The facade holds no domain rules, so a job or a\nconsumer can invoke the same use case.\nPure response mapping can happen after state is materialized; a remote facade does not\nby itself require a local database transaction or holding one across the remote call.\n\n**Where it fails:** leaving fine-grained remote calls in the client interaction or behind\nthe facade can retain network cost. Fine-grained local calls are a valid implementation;\nmeasure the actual hop topology before asserting unchanged latency.\n\n## Composition 4 — read/write split (no CQRS infrastructure)\n\n```text\nWRITE                                READ\nController                           Controller\n  └── Application service              └── Query object / projection\n      └── Repository (aggregate)            └── SQL / JPQL constructor expression\n          └── Domain Model                      └── Database (or a replica)\n              └── Database\n```\n\n**Consequences:** the write path keeps its invariants and its aggregate cost; the read path\ncan use a tailored projection with a measured query budget; both still share schema and\ndatabase constraints. Two interfaces over the primary do not require eventual consistency,\nbut a read replica may lag. State the freshness/isolation contract rather than infer it\nfrom the absence of a projection pipeline.\n\n**Where it fails:** treating it as a licence to write through the read path. The read side\nneeds enforceable write restrictions and actor/tenant/field authorization. A projection or\nquery repository can be suitable; having no entity or repository types does not prevent\nraw SQL writes or unauthorized reads. Check actual capabilities and affected bypass paths.\n\n**When to go further** — a separate read store, maintained asynchronously — is a much bigger\ndecision. Read load, query shape, workload isolation or independently owned access/lifecycle\nrequirements may justify it; the primary need not be incapable of running the query.\nCompare the actual benefit with asynchronous lag and its freshness/consistency contract,\na projection pipeline to operate, and a rebuild procedure (`consistency-models`).\n\n## The relationship graph\n\nCommon collaborators and tensions, not logical implications.
