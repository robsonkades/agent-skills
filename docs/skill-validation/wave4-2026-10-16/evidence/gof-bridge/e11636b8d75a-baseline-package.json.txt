When a design varies along two independent axes and both are\nexpressed as subclasses, the variation-specific class count is their product: `EncryptedS3Store`,\n`PlainS3Store`, `EncryptedFileStore`, `PlainFileStore`, and two more when one axis gains a third\nmember. Bridge makes one axis the abstraction, the other an implementor interface held in a field.\nThe variation implementations grow by their sum; shared interfaces and wiring add other types.\n\nMechanically this is \"hold an interface in a field and delegate\" — which is why the pattern is\nrarely named in Java code that already does it. Naming it is still worth something: it says the\nfield is not an incidental collaborator but the second axis of the design, and that new backends\nare expected to arrive without touching the abstraction.\n\nStart from representative consumer operations, required advanced capabilities and failure/lifecycle\nexpectations. Reuse accepted boundary decisions, change history and existing tests to establish the\ntwo responsibilities; names and type counts are clues. Ask only for missing evidence that could\nchange the legal combinations or contract, and retain adequate composition when a second hierarchy\nadds no useful separation.\n\n## When it is the answer\n\n```text\nTwo axes of variation can evolve independently and a product hierarchy\nwould couple their change rates\n        → Bridge is a candidate; compare plain composition and configuration.\n\nAn API you publish must outlive the mechanisms that implement it —\ndrivers, transports, backends contributed by others\n        → Separate the public contract from its providers. JDBC and SLF4J\n          illustrate API/provider boundaries; a Bridge classification still\n          depends on the independent roles in the design under review.\n\nThe abstraction has refinements that evolve independently of its\nimplementation mechanisms\n        → This makes the Bridge roles visible. Class count alone does\n          not distinguish it from Strategy; compare the design intent.\n```\n\n## When it is not\n\n- **Only an algorithm varies, with no independently evolving abstraction/provider boundary.**\n  Compare Strategy or plain composition; do not invent another hierarchy (`gof-strategy`).\n- **The abstraction is a single stable class and no refined abstraction is expected.** Plain\n  composition may describe it better, although the same separation can still protect a public\n  API from independently evolving providers.\n- **The implementor has one implementation and no boundary reason.** This weakens the case. Bridge separates evolving roles; it can be introduced during refactoring and use\n  adapters as implementors (`gof-adapter`). Timing or authorship alone does not decide the pattern.\n\n## Modern Java expression\n\nExamples target Java 17 without preview: sealed types and records are available. A uniform thread-safe contract simplifies substitution, but forced internal\n  synchronization can destroy affinity or throughput; factories that return confined sessions\n  are often a better bridge for stateful drivers.\n- **Lifecycle.** Define ownership of injected backends, sessions and returned streams/cursors,\n  including close responsibility on failure or cancellation. A borrowed shared backend is not\n  closed per call; a stream may outlive the method that returns it. Preserve affinity and the\n  actual operation's lifetime rather than inferring cleanup from a caller timeout.\n- **Binding.** Distinguish selecting a backend for a new abstraction or operation from replacing\n  one during a live session. A common interface does not make handles, stored data or deduplication\n  state portable. Notification kinds — `Alert`, `Digest`, `Receipt` — differ in how they are composed:\nan alert is one line with a severity, a digest batches events over a window, a receipt renders a\ndocument. Channels — email, SMS, push — differ in how bytes leave the process.\n\nPartial Java 17 sketches: domain types, imports and provider implementations are omitted.\nJUnit-shaped examples describe contract cases, not executed tests or standalone source files.\n\n## Before — the product\n\n```java\nabstract class Notification { abstract void send(); }\n\nclass EmailAlert   extends Notification { ... }\nclass SmsAlert     extends Notification { ... }\nclass PushAlert    extends Notification { ... }\nclass EmailDigest  extends Notification { ... }\nclass SmsDigest    extends Notification { ... }\nclass PushDigest   extends Notification { ... }\nclass EmailReceipt extends Notification { ... }\nclass SmsReceipt   extends Notification { ... }\nclass PushReceipt  extends Notification { ... }\n```\n\nNine classes for six concepts, and the composition logic for a digest is duplicated three times\n— so a fix to digest windowing is three edits, and the SMS one will be forgotten. Adding\nWhatsApp is three new classes; adding a fourth notification kind is another four.\n\n## After — independent roles through composition\n\n`Notifier` is the sending abstraction and `Channel` supplies its implementation mechanism.\n`Notification` is a separate content hierarchy: `Alert`, `Digest` and `Receipt` render messages;\nthey are not refined subclasses of `Notifier` and do not hold its channel. This design illustrates\nthe independent roles with composition instead of copying the classical Bridge hierarchy. A codebase\nthat already uses this shape need not add subclasses to fit a pattern diagram.\n\n```java\npublic interface Channel {\n    /**\n     * Submits a rendered message. A receipt confirms provider acceptance, not recipient delivery.\n     * Implementations are safe for concurrent use, honor the remaining deadline across retries,\n     * and stop initiating work when it expires. Local termination does not cancel a remote effect.\n     *\n     * @throws DeliveryRejected      permanent — bad address, payload too large\n     * @throws DeliveryUnavailable   temporary failure; effect may be unknown after transmission\n     */\n    DeliveryReceipt deliver(RenderedMessage message, Deadline deadline);\n\n    /** Per-input results in input order: accepted, rejected, unknown or not attempted.\n     *  Preserve successful prefixes and IDs; a transport failure must not erase partial progress.\n     *  Batch limits and chunking share the original deadline.\n     */\n    List<DeliveryOutcome> deliverAll(List<RenderedMessage> messages, Deadline deadline);\n\n    /** Immutable snapshot of advertised capabilities, not a reservation.\n     *  deliver/deliverAll must enforce current per-message constraints before the effect;\n     *  if an effect may already have occurred, preserve the unknown/partial outcome.\n     */\n    Set<MessageFeature> supported();\n}\n```\n\n```java\npublic sealed interface Notification permits Alert, Digest, Receipt {\n    RenderedMessage render();\n}\n\npublic final class Notifier {\n    private final Channel channel;\n\n    public Notifier(Channel channel) {\n        this.channel = java.util.Objects.requireNonNull(channel, \"channel\");\n    }\n\n    public DeliveryReceipt send(Notification notification, Deadline deadline) {\n        return channel.deliver(notification.render(), deadline);\n    }\n}\n```\n\nThree notification kinds plus three channels: six variation types instead of nine combined\nvariants, plus the shared interfaces and wiring. Variation grows by addition; digest windowing\nexists once. Total type count alone is not the benefit.\n\nThe final channel field binds each `Notifier` at construction; a later preference can select a\nnew notifier for a new send. This example does not implement live replacement, and a receipt's\nprovider message ID is not automatically valid on another provider. An ambiguous send requires\nits original outcome/retry contract, even if configuration now selects a different channel.\n\n## What the remote channel forced into the interface\n\nIn this illustrative scenario, email and SMS were HTTP-backed from the start, so `deliver` carries a\n`Deadline` and a documented transient/permanent split. Push was added later and delivers in\nbatches of up to 500 — which is why `deliverAll` exists rather than being discovered when a\ndigest run issued 40 000 individual calls. These limits and volumes are scenario assumptions,\nnot claims about every push provider. The single-message `Notifier.send` path below does not use\nthe batch API; a bulk caller must select `deliverAll` and preserve its per-input outcomes.\n\nTwo lessons that generalise:\n\n- **Bulk behavior needs a contract.** A sequential default can hide round trips and lose partial\n  success when item N throws. Each implementation must preserve outcomes, bound batching and\n  document whether acceptance is atomic. Retry unknown outcomes only with established provider\n  idempotency/deduplication semantics, scope and retention; reusing an ID alone proves nothing.\n- **`supported()` exists because of the holes.** A `Receipt` renders a PDF attachment, which SMS\n  cannot carry.     "Content": "# Deciding on Bridge\n\n## The N×M test\n\nWrite the two axes as a grid and fill in the class names that exist or would exist.\n\n```text\n                 S3        LocalFile    SFTP\nEncrypted    EncryptedS3  EncryptedFile  EncryptedSftp\nPlain        PlainS3      PlainFile      PlainSftp\nCompressed   ...          ...            ...\n```\n\nThree questions decide it:\n\n1. **Which members and independent change pressures are evidenced?** Multiple members make\n   the split visible; a concrete public-provider boundary may matter with one implementation.\n   Without a second responsibility or boundary need, a field or Strategy is enough.\n2. **Are they independent — is every cell meaningful?** If cells are illegal, see below.\n3. **Will both keep growing?** If one axis is closed and small, a sealed set with an exhaustive\n   `switch` may beat a second hierarchy.\n\nThese are evidence prompts, not mandatory counts. A concrete public boundary can justify one\ncurrent provider, a closed abstraction set can vary independently, and sparse legal combinations\ncan be encoded explicitly. Compare simpler composition rather than inventing future variants.\n\n## Bridge against its neighbours\n\n| Question                                                                            | Answer                    |\n| ----------------------------------------------------------------------------------- | ------------------------- |\n| A consumer abstraction and its implementation mechanisms need independent evolution | Bridge                    |\n| An existing interface must be translated to the consumer's required contract        | Adapter (`gof-adapter`)   |\n| Interchangeable algorithms vary behind the same operation contract                  | Strategy (`gof-strategy`) |\n| Several products that must come from the same family                                | Abstract Factory          |\n| Same interface in and out, behaviour added                                          | Decorator                 |\n| A hierarchy of things that contain each other                                       | Composite                 |\n\nBridge and Strategy can use the same delegation structure. Distinguish the responsibility being\nseparated: a consumer abstraction from independently evolving implementation mechanisms, or an\noperation from interchangeable algorithms. Refinements on the abstraction side help expose a Bridge,\nbut their absence does not make a public provider boundary necessarily Strategy. Neither two open\nhierarchies nor simultaneous authorship is required. Preserve adequate composition; documenting its\nroles can be more useful than settling a pattern label.\n\nBridge/Adapter differ in intent, not authorship or timing. Bridge separates evolving roles;\nAdapter translates an existing interface. Introducing a bridge while refactoring existing code\nand implementing its backend ports with adapters is a normal combination.\n\n## When the matrix has holes\n\nSome combinations are meaningless under a particular contract: a report stream cannot fit a\nsingle SMS payload, or an encrypted random-update store may require capabilities absent from an\nappend-only backend. Encryption alone does not require random access; name the actual operation.\n\nReject static illegal pairings at construction where possible. When legality depends on each\nmessage or current configuration, validate before the side effect and keep authoritative validation\nin the backend as needed; an earlier capability snapshot may be stale. The following are separate\nconstruction sketches: the first assumes an `Alert(Channel)` abstraction, unlike the render-only\n`Notification` input in the worked example. Static options include:\n\n```java\n// 1. Enumerate the legal pairs at the composition root\nstatic Notification alert(Severity s) {\n    return new Alert(s.isCritical() ? sms : email);      // only legal channels reachable\n}\n\n// 2. Type the capability, so illegal pairs do not compile\ninterface Channel {}\ninterface StreamingChannel extends Channel {\n    // Caller owns and closes the returned stream, including on write failure.\n    // Closing it does not close this borrowed, potentially shared channel.\n    OutputStream open();\n}\n\nrecord StreamingReport(StreamingChannel channel) { }     // SmsChannel cannot be passed\n```\n\nThe second is useful when capabilities are stable and few; the first when policy may change.\nStatic pair constraints belong where the pair is formed; per-input or changing constraints\nstill need validation at the operation that can enforce them. These capability types do not exclude\nnull; enforce required collaborators at the construction boundary. For a real stream API, also\ndeclare open/write/close failures, partial effects and any thread affinity; a returned stream's\nlifetime is not the duration of `open()`.\n\nIf constraints dominate the matrix, compare an explicit set of named legal combinations.\nSparsity alone does not invalidate a useful separation; price its capability and validation cost.\n\n## Designing the implementor interface\n\nDesign from required consumer operations and the costs/failures of the backends that must support\nthem. Preserve useful capabilities rather than reducing every provider to the weakest one:\n\n**Granularity.** An interface with `boolean exists(Key)`, `byte[] read(Key)`, `void write(Key,\nbyte[])` can produce expensive repeated calls when the abstraction loops over ten thousand\nremote keys. Inspect actual call patterns and available measurements; an adequate single lookup\ndoes not need a batch API merely because it is remote. When batching is justified, define size,\npartial-result and deadline semantics rather than assuming a loop is equivalent\n(`rpc-and-api-contracts`).\n\n**Failure.** A method that returns `void` and \"cannot fail\" locally will fail remotely. Decide up\nfront whether failure is an exception (with a documented transient/permanent split) or a result\ntype, and keep it uniform across backends (`java-exception-design`).\n\n**Time.** Both local and remote work can block. Name the deadline/cancellation owner and what is\nbounded: admission, new attempts, caller wait or actual local work. A deadline parameter or injected\npolicy can carry the contract; a timeout alone does not establish cleanup or undo a remote effect\n(`timeouts-and-deadlines`).\n\nExercise ordinary and advanced consumer calls against the materially different backends before\ncommitting the interface. Starting with a costly remote path can reveal missing constraints, but\ndoes not replace the consumer contract or force every capability onto every implementation.\n\n## Backend binding and replacement\n\nRead this when \"swappable\" means more than wiring a different provider for a new object. Establish\nwhen selection may change and what survives it: a method call, session, cursor, resource handle,\nstored object or retry identity. Keep constructor injection when it already meets the requirement;\na mutable backend field is not an improvement by itself.\n\nThe decisive constraint is whether the operation carries provider-owned state:\n\n- A renderer that accepts portable input and returns a self-contained value can select a\n  compatible backend for each independent call, if the contract permits it. There is no need\n  to invent session migration; sharing and resource ownership still apply.\n- If rendering returns a document handle for subsequent edits, pages and closure, keep those\n  calls with the owning backend/session unless transfer is explicitly supported. Re-reading a\n  mutable `currentBackend` for each call can mix instances. Even two instances of the same\n  provider class need not share resources or identity namespaces.\n\nThis distinction also occurs in standard APIs: a Java 17 `Path` identifies its creating file\nsystem through `getFileSystem()`, and `compareTo` rejects paths from different providers\n([Path contract](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/nio/file/Path.html)).\nThat is evidence against assuming arbitrary cross-provider interoperability, not a claim that\nevery operation or every Bridge has the same restriction.\n\nFor required live replacement, define admission to the new provider, the lifetime protection for\nold users, and who drains or terminates and closes the old provider. Capturing a reference once\navoids mixed dispatch but does not prevent another owner closing it. Use the project's existing\nsession/lease/ownership mechanism where adequate; do not prescribe a lock or hot-swap facility\nwithout the concurrency requirement. Test replacement between acquisition and use, including\nlate cleanup, rather than only two successful calls before and after the switch.\n\nFor storage or remote failover, establish retained-data access, identity and ambiguous-effect\nrecovery separately. Retrying through a new provider is not safe merely because the original\nprovider deduplicates that ID.
