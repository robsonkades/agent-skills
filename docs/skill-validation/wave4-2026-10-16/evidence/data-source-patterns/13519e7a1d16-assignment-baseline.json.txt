Data Mapper separates\naccess from the objects it stores. A close table shape does not make an entity Active Record;\na separate mapper can map that same shape. Mapping capabilities and rule purity affect the\ncost of independence, so inspect them rather than treating this table as a guarantee.\n\n| Dimension                     | Active Record                                       | Data Mapper                                    |\n| ----------------------------- | --------------------------------------------------- | ---------------------------------------------- |\n| Object/table divergence       | often close; framework mapping may allow divergence | separates shape translation                    |\n| Lines of code for simple CRUD | can be compact                                      | framework may supply mapping                   |\n| Schema change impact          | may affect domain and access together               | can be localized, not guaranteed               |\n| Domain change impact          | migration only if persisted representation changes  | same persistence-contract constraint           |\n| Unit-testing a rule           | pure methods need no database                       | pure methods need no database                  |\n| Query control                 | depends on API and exposed SQL                      | depends on mapper and query API                |\n| Ownership of the schema       | influences ease of evolution, not a prerequisite    | supports independent translation               |\n| Aggregates spanning tables    | awkward                                             | natural                                        |\n| Value objects and rich types  | limited by column mapping                           | natural                                        |\n| Cognitive load                | access and rules share a class                      | mapping complexity; a second model is optional |\n| Common failure                | schema drives the model                             | mapper becomes a second domain model           |\n\n## The same domain both ways\n\nThe rule: an invoice may be settled only if the payment currency matches and the amount\ncovers the outstanding balance.\n\nThe following Java 17 snippets are partial: constructors, imports, identifiers, money,\nstatus and exception types are omitted. The primitive\nfields are an illustrative modeling choice, not a JPA requirement. Value objects can use\nembeddables or suitable converters; evaluate their mapping and query constraints before\nadding a second model. The shown `settle` method can be unit tested without EntityManager.\n\n### Separate domain model and mapper\n\n```java\n// Domain: no annotations, no framework, no persistence.\npublic final class Invoice {\n    private final InvoiceId id;\n    private Money outstanding;\n    private InvoiceStatus status;\n    private long version; // preserve the loaded optimistic-lock token through mapping\n\n    public void settle(Money payment) {\n        if (!payment.currency().equals(outstanding.currency()))\n            throw new CurrencyMismatch(outstanding.currency(), payment.currency());\n        if (payment.isLessThan(outstanding))\n            throw new PartialSettlementNotAllowed(id);\n        outstanding = Money.zero(outstanding.currency());\n        status = InvoiceStatus.SETTLED;\n    }\n}\n\n// Mapper: the only code that knows both shapes.\n@Component\nfinal class InvoiceMapper {\n    Invoice toDomain(InvoiceRow row) {\n        return Invoice.reconstitute(new InvoiceId(row.id()),\n            Money.of(row.outstanding(), Currency.getInstance(row.currency())),\n            InvoiceStatus.valueOf(row.status()), row.version());\n    }\n    InvoiceRow toRow(Invoice invoice) { ... }\n}\n```\n\nThe rule reads in the business's language and the mapper can isolate column renames.\nPreserve identity and carry the loaded version as the expected token for the write; replacing\nit with a newly read version conceals a stale-write conflict. When updating through a managed\nJPA entity, compare its loaded version with that expected token before copying domain changes,\nreject a mismatch, and let the provider maintain `@Version`. Do not overwrite the managed\nversion field to force acceptance. The provider's write-time check still guards races after\nthe comparison; failure may surface at flush or commit, not at the setter call.\n\nFor a custom SQL mapper, put the expected version in the write predicate and require the\nintended affected-row count; a single-row update returning zero has not succeeded. Use an appropriately accessible\nfactory without weakening creation invariants.\n\n## Read shape and write intent\n\nA mapper may return a deliberately lossy read projection. That does not make the projection\na safely reconstituted aggregate. For example, an invoice summary containing ID, label and\nversion has no evidence about its outstanding balance, currency or lines. Filling those gaps\nwith nulls, zero money or an empty collection creates asserted state, not loaded state.\nEven a matching version cannot detect that the application supplied an incomplete state.\n\nChoose the write contract deliberately:\n\n- For a command whose invariant needs existing state, load that state and apply the command\n  within the chosen concurrency/transaction boundary. This need not load every relationship;\n  load what the invariant actually depends on. Keep validated creation factories/constructors and controlled\n  mutation; these requirements do not make constructor invariants impossible.\n- Bidirectional associations are added for mapping reasons and become part of the domain\n  API.\n- Inheritance is chosen for what maps well rather than for what the business means\n  (`inheritance-mapping-strategies`).\n- The entity is serialised directly to the API, coupling three things at once\n  (`remote-facade-and-dto`).\n- The model cannot be tested without an `EntityManager`, so tests become slow and\n  integration-shaped.\n\nThe honest options are to accept the middle ground and record it, or to separate domain\nfrom persistence model and pay for the mapper. Both are defensible; only the unexamined\nversion is not (`architecture-decision-making`).\n\n## Choosing\n\n```text\nDo you own the schema and will it follow the model?\n├── no → Rich domain needs isolation? Reporting or\n│         transaction scripts may only need a gateway/projection.\n└── yes → Do the business rules interact, or need types the columns\n          cannot express (Money, ranges, state machines)?\n          ├── no  → Active Record or a simple mapper, matching access ownership.\n          └── yes → Do mapping constraints interfere with the desired model,\n                    or is independent evolution valuable based on actual changes?\n                    ├── no  → JPA entities with rules on them (the middle\n                    │         ground). Use Java 17 and Spring 6.1+\nfor `JdbcClient`; JPA annotations/API here use `jakarta.persistence` on that stack.\n\n## Table Data Gateway\n\nOne object holds every SQL statement for one table. It speaks in primitives, records or\nrow objects — never in domain objects — and contains no business rules.\n\n```java\n@Repository\npublic class RateGateway {\n\n    private final JdbcClient db;\n\n    RateGateway(JdbcClient db) { this.db = db; }\n\n    public Optional<RateRow> find(String origin, String destination) {\n        return db.sql(\"\"\"\n                SELECT id, origin, destination, per_kg, valid_from, valid_to\n                  FROM rate\n                 WHERE origin = :origin AND destination = :destination\n                   AND valid_from <= CURRENT_DATE AND valid_to > CURRENT_DATE\n                \"\"\")\n            .param(\"origin\", origin)\n            .param(\"destination\", destination)\n            .query(RateRow.class)\n            .optional();\n    }\n\n    public int expireAllFor(String origin, LocalDate on) {\n        return db.sql(\"UPDATE rate SET valid_to = :on WHERE origin = :origin AND valid_to > :on\")\n            .param(\"on\", on).param(\"origin\", origin)\n            .update();\n    }\n}\n\npublic record RateRow(long id, String origin, String destination,\n                      BigDecimal perKg, LocalDate validFrom, LocalDate validTo) { }\n```\n\n### What belongs here\n\nSQL, parameter binding, row mapping, technical validation and affected-row/error handling.\n`find` assumes at most one currently valid rate per route: `.optional()` throws on multiple\nrows, rather than choosing one. Enforce that invariant in the database or return a collection\nwhen multiple matches are valid. `CURRENT_DATE` uses the database's date/time context; bind\nan explicit business date if the caller owns that policy.\n\n`expireAllFor` is a partial SQL illustration: define whether future rates may be shortened\npast their start date, and preserve interval constraints. Bulk SQL bypasses entity callbacks\nand automatic entity version checks; preserve version predicates/updates required by the\nwrite contract and test against the target dialect.\n\nWhen mixing a gateway with managed JPA entities in one use case:\n\n- Verify that both join the intended transaction. In Spring, `JpaTransactionManager` can\n  expose its connection to JDBC using the corresponding `DataSource`, transaction-aware\n  lookup and a compatible `JpaDialect`. `JdbcClient` delegates to Spring JDBC; `@Repository`\n  alone neither starts a transaction nor enlists an arbitrary connection. Force a failure\n  after both writes and verify that both roll back (`enterprise-transactions`).\n- Do not assume plain JDBC triggers JPA auto-flush. If SQL must observe pending entity changes,\n  deliberately flush them first within the shared transaction. Flush does not commit it.\n- After SQL changes managed rows, reconcile before relying on those objects again. `clear`\n  detaches all managed entities and loses unflushed changes; `refresh` overwrites the selected\n  entity's state. Preserve intended changes before SQL/invalidation, or isolate the bulk work\n  in a suitable fresh persistence context. Do not blindly flush stale objects after SQL.\n  Provider caches may also need invalidation; runtime policy belongs to `orm-behavioral-patterns`.\n\n### What must not\n\nConditionals that encode a business rule. The moment a gateway method contains\n`if (row.status().equals(\"BLOCKED\")) return Optional.empty();`, a rule has moved into the\ndata layer with unclear ownership. Expose policy deliberately, for example by returning the\nrow for a caller decision or by naming an explicit policy-filtered query. A concurrency\nguard in an atomic write must remain in SQL; moving it to a prior read can introduce a race.\n\n### Where it is the best available option\n\n- Reporting and exports — the query is the logic.\n- Bulk operations — `expireAllFor` above is one statement instead of N object loads\n  (`architecture-and-performance`).\n- Integrations against a schema you do not own.\n- Any path where the exact SQL and its plan matter enough to be reviewed.\n\n### How it degrades\n\nBy mixing unrelated access responsibilities or hiding policy decisions. Inspect callers,\nSQL predicates and change reasons; a method count or grep for `if` is not a diagnosis.\n\n## Row Data Gateway\n\nOne object per row, holding the row's fields and its own load/save, with **no business\nlogic**. In modern Java it appears mainly as a deliberate boundary rather than as a chosen\npattern, and naming it is useful:\n\n```java\n// Passive row data only: this is NOT a Row Data Gateway by itself.\npublic record CustomerRow(Long id, String name, String email, String status, long version) { }\n```\n\nThe record above has no database access. A Row Data Gateway additionally owns row-level\ninsert/update/delete operations (with affected-row/version checks and a caller-owned\ntransaction). A mapper returning a passive record does not turn it into a gateway.\nWhen a class named `Customer` contains only accessors plus\npersistence, the design has a Row Data Gateway that is being described as a domain model —\nand the business rules are therefore somewhere else, usually a service\n(`domain-logic-organization`).\n\n## Active Record\n\nThe row object plus the business logic for that row. Persistence is a method on the object.\n\n```java\n@Entity\n@Table(name = \"subscription\")\npublic class Subscription {\n\n    @Id @GeneratedValue private Long id;\n    private Long customerId;\n    @Enumerated(STRING) private SubscriptionStatus status;\n    private LocalDate renewsOn;\n    private BigDecimal monthlyPrice;\n    @Version private long version;\n\n    // Assumed policy: cancellation is allowed through renewsOn minus three days, inclusive.\n    public void cancel(LocalDate on) {\n        if (status == CANCELLED) throw new AlreadyCancelled(id);\n        if (on.isAfter(renewsOn.minusDays(3))) throw new CancellationTooLate(id);\n        status = CANCELLED;\n    }\n\n    // Persistence on this object makes this sketch Active Record.\n    // For a new instance only; caller owns the EntityManager and transaction.\n    public void insert(EntityManager em) { em.persist(this); }\n\n    public BigDecimal proratedRefund(LocalDate on) { ... }\n}\n```\n\nWithout the persistence method, an entity with `cancel` and an external repository remains\nData Mapper-style persistence, even if it closely mirrors a table. That ownership difference\nis substantive. The `insert` sketch illustrates coupling, not a recommendation to inject an\nEntityManager into existing entities. Pure `cancel` tests do not require a database; insertion,\nflush/commit failures and optimistic locking require integration tests.\n\n### When Active Record is the right call\n\n- The schema is yours and follows the model.\n- One concept, one table — the mapping is an identity function.\n- The rules are per-row: validation, status transitions, derived values.\n- The module is small enough that a mapping layer would be its largest component.\n\nCRUD-heavy admin areas, configuration modules and reference data are the natural home, and\nusing it there is a deliberate decision worth recording rather than an admission.\n\n### Where it stops working\n\n| Signal                                                             | What it means                                  |\n| ------------------------------------------------------------------ | ---------------------------------------------- |\n| A concept needs data from three tables to decide anything          | The object is no longer the row                |\n| The class has fields that exist only because the table has columns | The schema is shaping the model                |\n| Business rules span two Active Records and land in a service       | The model has outgrown per-row logic           |\n| A schema change forced by a report changes the domain class        | Reporting is now coupled to the business model |\n| Unit tests need a database to exercise a rule                      | The rule is entangled with persistence         |\n| The same class is used as the HTTP payload and the row             | The public API is now the schema               |\n\nUse the observed cost and affected behavior to decide whether to move to a Data Mapper\n(`active-record-vs-data-mapper.md`), and the migration is incremental\n(`architecture-refactoring-paths`).\n\n### Two things Active Record does not excuse\n\n- **Serving as the API payload.** Active Record couples object to table; exposing it\n  couples the public contract to the table as well, and that is a third coupling nobody\n  decided on (`remote-facade-and-dto`).\n- **Skipping the transaction boundary.** Logic on the object does not remove the need for a\n  use case that demarcates the transaction when more than one object is written\n  (`enterprise-transactions`).\n\n## Choosing between the three in one module\n\n```text\nDoes the code make business decisions about this data?\n├── no  → gateway (table or row), or a projection mapper; If it is externally owned, inspect actual constraints and change\n   history: isolate translation when domain behavior needs independence, without inventing a domain model for reports.\n4. **Check the work shape.** Consider a SQL gateway for set-based or reporting work when\n   query control, translation or measured cost warrants it. An existing ORM projection or\n   bulk query may already fit; validate its invariant, versioning and managed-state effects\n   before adding another access layer. For mixed JDBC/JPA paths, verify transaction participation\n   and flush/context visibility; sharing a database URL does not prove atomicity.\n5. **Decide per module.** A pricing engine with a mapper and an admin CRUD area with Active\n   Record in one application is a reasonable design, provided the boundary between them is\n   explicit.\n6. **Write down what the choice couples**, so the next person understands the cost of\n   changing it.\n\n## Decision rules\n\n```text\nTransaction scripts, set-based work, reporting, imports\n        → Consider Table Data Gateway for explicit set-oriented access.\n          Keep business-policy ownership outside it; technical checks are allowed.\n\nSimple CRUD, schema mirrors the model, you own the schema, thin rules\n        → Active Record is a candidate if persistence methods on the\n          object fit the existing stack; a simple mapper is also reasonable.\n\nRich interacting business rules; model and schema will diverge\n        → Data Mapper. This is what the pattern exists for and the cost\n          is the mapping layer.\n\nSchema owned elsewhere, or legacy, or shaped for reporting\n        → Mapper plus translation when a domain model needs isolation;\n          a read/reporting gateway may suffice. Do not let the foreign schema\n          become the model (legacy-enterprise-modernization).\n\nDomain model already chosen, and the schema currently matches it\n        → JPA entities are a Data Mapper whose mapping is declarative.\n          Acceptable and common; the risk is that the annotations start\n          shaping the model (orm-structural-mapping).\n\nRules need testing without a database\n        → First isolate rule execution from I/O. Both a JPA entity and an\n          Active Record can have pure rule methods. Add a separate domain\n          model only when mapping constraints justify it.\n\nRead path of an application whose write path uses a mapper\n        → Consider a gateway/projection when loading the write model adds\n          measured cost; ordinary aggregate reads remain legitimate.\n```\n\n## Rules\n\n- **Active Record is not a beginner's pattern.** A close object/row correspondence and\n  simple rules can make combined access and behavior economical. Revisit when observed\n  mapping or testing constraints obstruct the model, rather than on a pattern label alone.\n- Active Record combines persistence and domain behavior in one object, often keeping a\n  close row shape. Mapping features can absorb column renames or value types; inspect actual\n  change propagation rather than asserting every domain change needs a migration.\n- Data Mapper's real cost is the mapping layer: code to write, code to test, and a place\n  for bugs that neither the model nor the schema exhibits alone. It is worth paying when\n  independence or mapping complexity warrants it, even when current shapes happen to match.\n- A JPA entity without persistence methods remains part of a Data Mapper-style unit of work, even\n  when persistence constraints distort its design; call that **persistence leakage**, not Active\n  Record. If the model has an `Integer` where the domain means an enum, a flattened\n  address because `@Embeddable` was awkward, or a bidirectional association that exists\n  only for a mapping, the schema is already shaping the model — decide deliberately whether\n  that is acceptable here.\n- Do not build a DAO layer that wraps a repository that wraps the ORM. Each layer must add\n  behaviour — a translation, a policy, an aggregate boundary — or it is indirection\n  (`enterprise-architecture-smells`).\n- Table Data Gateway pairs with transaction scripts. Resource handling, row-count checks,\n  SQL predicates and optimistic concurrency checks are legitimate conditionals. Hidden\n  business-policy decisions migrating into the gateway are the concern, and\n  it is hard to find later because nobody looks for rules in a data-access class.\n- Row Data Gateway is rarely chosen deliberately today, but it names a useful boundary: a\n  row object with no business logic. When a \"domain object\" has only accessors and\n  persistence, that is what it is, and calling it that clarifies the design\n  (`domain-logic-organization`).\n- Different patterns may coexist. Multiple mechanisms can write one table during migrations or for\n  deliberately partitioned operations, but they must share invariant, versioning and transaction\n  rules with explicit write authority. Uncoordinated writers are the defect\n  (`offline-concurrency-control`).\n- SQL can avoid object loading for reporting and bulk changes; verify plans, rows touched,\n  round trips and application latency. Set-based writes must preserve invariants, versioning\n  and transaction semantics; ORM callbacks and managed state may be bypassed. Decide flush\n  and invalidation order before direct SQL; `clear` can discard unflushed entity changes.\n- Treat a read projection and a writable model as different contracts. Missing columns are\n  not evidence for null, zero or empty domain state. Before saving a reconstructed object,\n  establish which fields the command owns and which state its invariants need. An identity\n  and version token alone do not make a partial object safe to write back; compare loading\n  the required state with a narrowly scoped conditional update.\n\nDeliver a pattern choice grounded in one representative read/write path, ownership and\ncoupling costs, plus a validation case and revisit trigger. If schema or lifecycle evidence\nis missing, state the conditional choice instead of prescribing a migration.\n\n## References\n\n- [Gateways, Row Data Gateway and Active Record](references/gateways-and-active-record.md)\n  — each pattern implemented in modern Java, what belongs in each and what must not, where\n  the gateway degrades, Active Record in a Spring stack and its honest limits, and the\n  signals that a pattern has been outgrown.
