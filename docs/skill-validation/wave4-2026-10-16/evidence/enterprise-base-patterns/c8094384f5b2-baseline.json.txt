Most of\nthese patterns are one class each. Their value is not complexity; it is that each one has a\nknown cost and a known failure mode.\n\n## The patterns, in one line each\n\n```text\nGateway              an object that encapsulates access to an external\n                     system or resource, presenting it in your terms.\n\nMapper               an object that moves data between two subsystems\n                     while keeping them ignorant of each other.\n\nLayer Supertype      a common superclass for all types in a layer,\n                     holding what genuinely all of them need.\n\nSeparated Interface  the interface is separate from its implementation,\n                     owned by callers or an independent contract module.\n\nRegistry             a well-known object other objects use to find\n                     common services; its access and lifetime need a scope.\n\nSpecial Case         a type providing behaviour for a special case\n                     (usually \"absent\"), so callers stop branching.\n\nPlugin               links a class chosen at configuration time rather\n                     than at compile time.\n\nService Stub         a stand-in for an external service, so tests do not\n                     depend on it.\n```\n\n## Workflow\n\n1. **Name the problem before the pattern.** Inspect representative callers, existing seams,\n   ownership and compatibility requirements. Keep an adequate design; a small pattern can\n   still change failure handling, wiring or resource ownership.\n2. **For an external dependency, assess the needed seam.** Reuse a suitable port or client;\n   add a Gateway when translation, policy or isolation earns the extra boundary.\n3. **For a repeated null or default check, consider Special Case** when the affected\n   domain operations have an agreed default contract across callers.\n4. **For an interface with one implementation, identify the contract it protects:** inversion,\n   testing, API narrowing or supported extension (`layering-and-boundaries`).\n5. **Prefer direct injection for fixed collaborators.** Distinguish an ambient service locator\n   from an explicitly injected, scoped registry whose responsibility is dynamic lookup.\n6. **Match test doubles to the assertion.** Cover relevant success and failure outcomes across\n   caller tests; test protocol translation at the actual adapter boundary.\n\nFor Java examples, inspect Maven/Gradle release settings, toolchains and resolved Spring/Boot\nand persistence versions; do not upgrade the project to fit them. Name its actual contract rather than claiming full independence.\n- Gateways can make business-relevant time, identity and storage controllable in tests.\n  Reuse `Clock`, an id generator or a file-store boundary where needed; controlling these\n  inputs does not establish determinism for other concurrent or external work (`architecture-testing`).\n- **Layer Supertype fails by accretion.** It starts with an identifier and ends with twelve\n  protected helpers, at which point every subclass depends on things it does not use.\n  Review it whenever a method is added: does _every_ subtype need this?\n- **Separated Interface controls dependency direction.** Caller-owned ports are one use;\n  a framework-free contract module shared by independent consumers can also be appropriate.\n  Verify imports and public compatibility; package placement alone does not establish the\n  runtime wiring or the full ports-and-adapters contract\n  (`layering-and-boundaries`).\n- **Ambient Registry lookup hides dependencies.** An injected registry can make dynamic\n  selection explicit; define key/tenant scope, missing entries, mutation and provider cleanup\n  ownership.     "Content": "# Gateway and Mapper\n\n## Gateway\n\nAn object that encapsulates access to an external system and presents it in **your** terms.\n\n```java\n// The port: declared where it is used (Separated Interface), in your language.\npublic interface CreditBureau {\n    CreditAssessment assess(TaxId taxId, Money requestedLimit);\n}\n\npublic sealed interface CreditAssessment {\n    record Approved(Money limit, Instant validUntil) implements CreditAssessment { }\n    record Declined(DeclineReason reason)            implements CreditAssessment { }\n    record Unavailable(Optional<Duration> retryAfter) implements CreditAssessment { }\n}\n```\n\n```java\n// The gateway: the only place that knows the vendor exists.\n@Component\nclass HttpCreditBureau implements CreditBureau {\n\n    private final RestClient client;\n\n    HttpCreditBureau(RestClient client) { this.client = Objects.requireNonNull(client); }\n\n    @Override\n    public CreditAssessment assess(TaxId taxId, Money requestedLimit) {\n        try {\n            var response = client.post()\n                .uri(\"/v3/assessments\")\n                .body(new BureauRequest(taxId.digits(), requestedLimit.amount()))\n                .retrieve()\n                .body(BureauResponse.class);\n\n            if (response == null || response.decision() == null) {\n                throw new UnexpectedBureauResponse(\"missing decision\");\n            }\n\n            return switch (response.decision()) {                  // their vocabulary…\n                case \"APPROVE\" -> new Approved(                     // …becomes yours\n                    Money.of(response.limit(), \"BRL\"), response.validUntil());\n                case \"DECLINE\" -> new Declined(reasonFrom(response.code()));\n                default -> throw new UnexpectedBureauResponse(response.decision());\n            };\n        } catch (HttpServerErrorException | ResourceAccessException e) {\n            return new Unavailable(Optional.empty()); // retry delay not known\n        } catch (RestClientException e) {\n            throw new BureauIntegrationFailure(\"assessment failed\", e);\n        }\n    }\n}\n```\n\nThe partial adapter assumes static imports of CreditAssessment's nested outcomes, configured\nRestClient base URL/timeouts, domain-owned exceptions and vendor DTO/mapping helpers. It assumes\na BRL-only contract; validate requested currency and every required response field in those\nhelpers. Unknown retry delay is not permission to retry. Classify 429/Retry-After and permanent\n4xx/authentication failures from the actual vendor contract rather than calling every error a\nbusiness decline. Keep exception causes for restricted diagnostics, not client payloads.\nHere `Unavailable` means no usable assessment was obtained, not that the POST had no effect.\n\nThree things this does that a thin wrapper does not:\n\n1. **Translates the vocabulary.** Callers never see `\"APPROVE\"`, a bureau status code, or a\n   `BureauResponse`.\n2. **Translates the failures.** An HTTP 503 becomes `Unavailable`, a domain-meaningful\n   outcome the caller can handle without importing an HTTP library\n   (`layering-and-boundaries`).\n3. **Contains the vendor.** Replacement is local if the new provider satisfies the port's\n   semantics; otherwise the contract and its callers also need review.\n\n**Where resilience belongs:** timeouts and connection pooling on the client; retry and\ncircuit breaking around the gateway call, not inside the domain\n(`timeouts-and-deadlines`, `retries-and-backoff`, `concurrency-limiting-and-bulkheads`).\nAvoid waiting through remote retries while holding an unrelated database transaction: it can\nretain connections or locks throughout that budget. Inspect the actual transaction scope and\nresource acquisition (`enterprise-transactions`). Before retrying a POST, establish applicable\ndeduplication or reconciliation for all attempts and effects (`idempotency`). A transport failure\ndoes not prove that the provider did no work; a later refusal does not resolve an earlier attempt.\n\n**What a bad gateway looks like:** it returns `BureauResponse`, throws\n`HttpClientErrorException`, and takes the vendor's request type as a parameter. The\ndependency remains in every caller. That fails a promised domain-isolation boundary; retain a\nthin wrapper only if another concrete responsibility, such as policy or resource ownership,\njustifies it.\n\n## Gateways for time, identity and files\n\nUse controllable boundaries for business-relevant time, identity and storage:\n\n```java\n// Time: inject a Clock. Never call Instant.now() inside a business rule.\npublic Order cancel(Clock clock) { this.cancelledAt = Instant.now(clock); ... }\n\n// Identity: an interface, so tests are deterministic.\npublic interface IdGenerator { OrderId nextOrderId(); }\n\n// Files and object storage: your terms, not the SDK's.\npublic interface DocumentStore {\n    DocumentRef store(DocumentContent content);\n    Optional<DocumentContent> fetch(DocumentRef ref);\n}\n```\n\nThese let tests control the corresponding inputs or effects. Other concurrent work and real\nadapters still need their own evidence (`architecture-testing`).\n\n## Service Stub\n\nThe gateway's interface lets a stub supply the outcomes a caller test needs:\n\n```java\nfinal class StubCreditBureau implements CreditBureau {\n\n    private record Request(TaxId taxId, Money requested) { }\n    private final Map<Request, CreditAssessment> canned = new HashMap<>();\n\n    @Override public CreditAssessment assess(TaxId taxId, Money requested) {\n        var response = canned.get(new Request(taxId, requested));\n        if (response == null) throw new IllegalStateException(\"Unconfigured bureau request\");\n        return response;\n    }\n\n    void answers(TaxId taxId, Money requested, CreditAssessment response) {\n        canned.put(new Request(taxId, requested), Objects.requireNonNull(response));\n    }\n}\n```\n\nConfigure `Approved`, `Declined` or `Unavailable` for each expected request. This input-sensitive\nstub rejects an unknown request instead of inventing a business decline, exposing wrong caller\narguments or missing setup. Its request keys rely on stable value equality for `TaxId` and `Money`.\nA deliberate answer for all inputs can serve a different test; it does not verify argument forwarding.\n\nA successful stub can serve a focused test. Across the relevant tests, exercise the declared\nfailure outcomes as well; passing caller tests do not establish provider or transport behavior.\n\nThis mutable stub is test-instance scoped and not thread-safe. It tests caller reactions to\nport outcomes; it cannot test HTTP decoding or error translation. Exercise the adapter separately\nwith controlled HTTP responses (empty/malformed payload, 429, 4xx, 5xx and transport failure).\n\n**Check for contract drift** using existing provider verification and applicable integration\ntests. Run real-service checks only in an authorized environment with bounded effects and\nappropriate credentials; choose cadence from the provider/change contract. If access is\nrestricted, use available contract evidence and record what remains unverified\n(`architecture-testing`).\n\n## Gateway versus adapter\n\nThe words are used interchangeably and the distinction is still useful:\n\n```text\nGateway    a class that encapsulates an external resource. The term\n           describes what it wraps.\n\nAdapter    (hexagonal sense) the implementation of a port, living\n           outside the application core. The term describes where it\n           sits in the architecture.\n```\n\nA gateway implementing a port declared by the domain **is** a driven adapter. Use whichever\nvocabulary your codebase already uses, and do not run both\n(`layering-and-boundaries`).\n\n## Mapper\n\nAn object that moves data between two subsystems while keeping them ignorant of each other.\n\n```java\n// Neither Order nor OrderRow knows the other exists; the mapper knows both.\n@Component\nfinal class OrderMapper {\n\n    Order toDomain(OrderRow row, List<OrderLineRow> lines) {\n        return Order.reconstitute(\n            new OrderId(row.id()),\n            new CustomerId(row.customerId()),\n            OrderStatus.valueOf(row.status()),\n            lines.stream().map(this::toLine).toList(),\n            row.version());\n    }\n\n    OrderRow toRow(Order order) { ... }\n}\n```\n\n### Two rules\n\n**Use a Mapper to preserve subsystem independence.** If one side may depend on the other\nand you own its source, compare a constructor or static factory with a separate translation\nclass. Generated or third-party types may not be editable, even when dependency direction\nallows it. A separate translator can also centralise shared conversion or generated mapping;\nname that responsibility rather than asserting that every class called a mapper isolates\ntwo independent models (`data-source-patterns`).\n\n**A mapper must not invent business policy.** Faithful parsing, units and representation\nconversion still require logic, including rejection of malformed or lossy inputs. Keep those\nrules with the boundary contract; separate decisions such as eligibility or pricing.\n\n```java\n// Wrong: a business rule inside a translation.\nOrderView toView(Order order) {\n    return new OrderView(order.id(),\n        order.total().isGreaterThan(THRESHOLD) ? \"PRIORITY\" : \"STANDARD\",   // ← a rule\n        order.lines().size());\n}\n```\n\n`PRIORITY` is a business classification in this example. Hiding it in a mapper can obscure\nownership and duplicate the rule in another representation. Compute it in the agreed domain\nor use-case policy and map the result; inspect existing tests rather than assuming it is untested.\n\n## Where mappers accumulate\n\nA codebase with entity → domain → DTO → response has three mappers and two of them are\nfrequently identity functions.     "Content": "# Structural Base Patterns\n\n## Layer Supertype\n\nA common superclass for all types in a layer, holding what genuinely all of them need.\n\n```java\n@MappedSuperclass\npublic abstract class AggregateRoot<ID> {\n\n    @Version private long version;\n\n    public abstract ID id();\n    public long version() { return version; }\n}\n```\n\nThis partial JPA sketch is justified only for roots sharing this identity accessor and\noptimistic-version policy. Equality is deliberately not centralised: two unassigned ids must\nnot make distinct transient entities equal, and runtime `getClass()` checks can conflict with\nORM proxies. Choose and test identity across transient, persisted, detached and proxied states\nwith `java-object-contracts`; a shared superclass alone provides no equality guarantee.\n\n**How it fails:** accretion.\n\n```java\npublic abstract class BaseService {\n    @Autowired protected EntityManager em;              // now every service has one\n    protected void audit(String action) { ... }         // used by 3 of 20 subclasses\n    protected <T> T retry(Supplier<T> work) { ... }     // used by 2\n    protected LocalDate today() { ... }                 // hides an injected Clock\n}\n```\n\nEvery subclass now depends on the union of everyone's needs, `em` is reachable from classes\nthat should not touch it, and `today()` makes time untestable. The rule that prevents this:\n**a member may live in the supertype only if every subtype needs it.** Anything else is a\ncollaborator to inject.\n\n## Separated Interface\n\nSeparate the interface from its implementation. Caller-owned placement is useful when\ninverting a dependency:\n\n```text\ncom.acme.orders.domain\n    Orders.java              ← interface, owned by the domain\ncom.acme.orders.persistence\n    JpaOrders.java           ← implementation, depends on the domain\n```\n\nThe dependency now points from persistence to domain, not the reverse. An independently owned\ncontract module is another valid location when several consumers/providers share a stable API.\nCheck the actual dependency graph and compatibility obligations before moving it\n(`layering-and-boundaries`).\n\n**Cost:** the implementation is not discoverable from the interface without tooling, and\nwiring must be explicit, through manual construction or configuration. Both are acceptable at a real\nboundary and pure friction at a fake one — an interface with one implementation, no\ninversion, and no seam is a file (`enterprise-architecture-smells`).\n\n## Registry\n\nA well-known object other objects use to find common services.\n\n```java\n// A registry: a global with a nicer name.\npublic final class ServiceRegistry {\n    private static final Map<Class<?>, Object> SERVICES = new ConcurrentHashMap<>();\n    public static <T> T get(Class<T> type) { return type.cast(SERVICES.get(type)); }\n}\n```\n\n**Costs of this static locator:** dependencies vanish from constructors, so a class's real requirements are\ninvisible; tests become order-dependent and must remember to reset it; and concurrent access\nneeds care. In an application with dependency injection, almost every use is avoidable.\n\n**Distinguish scoped lookup:** an injected plugin registry can legitimately select by a runtime\nkey while keeping the lookup dependency visible. Prefer direct injection for fixed collaborators;\nwhere ambient lookup is unavoidable, keep it narrow and replaceable in tests. For either form,\ndefine key/tenant scope, missing-entry behavior, mutation and who closes providers. Protect actual\ncompound operations when shared; `ConcurrentHashMap` alone does not define lifecycle or isolation.\n\n`ApplicationContext.getBean()` inside business code is the same pattern with the framework's\nname on it, and carries the same costs (`layering-and-boundaries`).\n\n## Special Case\n\nA type providing behaviour for a particular case, so callers stop branching.\n\n```java\npublic sealed interface Customer permits RegisteredCustomer, GuestCustomer {\n    Money discountFor(Money amount);\n    boolean canPayOnAccount();\n}\n\npublic record GuestCustomer() implements Customer {\n    @Override public Money discountFor(Money amount) { return Money.zero(amount.currency()); }\n    @Override public boolean canPayOnAccount() { return false; }\n}\n```\n\nTwenty callers stop writing `if (customer == null || !customer.isRegistered())`.\n\n**The condition that justifies it:** the affected domain operations have an agreed contract\nacross callers. A guest's zero discount and inability to pay on account can remain uniform\nwhile a UI displays a guest-specific message. Repeated type tests that reimplement those\npolicies indicate a misplaced contract; distinguishing a case for presentation does not alone\ninvalidate the pattern. Where callers own different absence decisions, retain `Optional` or\nexplicit outcomes instead of forcing one default.\nEstablish the case first: a known guest is different from an unresolved customer lookup.\nDo not convert a failure into guest privileges or silently change authorization behavior.\n\n```text\nOptional<T>     at a boundary, where the caller must decide what absence means.\nSpecial Case    inside the model, where absence has uniform, real behaviour.\nNull            only where the existing interop contract requires it;\n                handle it explicitly before business use.\n```\n\nA sealed interface can combine polymorphic domain operations with explicit variant handling\nwhere needed. Exhaustive type-pattern `switch` requires Java 21 without preview; it does not\nremove the need to keep shared policy in one owner (`patterns-and-modern-frameworks`).\n\n## Plugin\n\nLink an implementation chosen at configuration time rather than at compile time.\n\n```java\npublic interface TaxCalculator { Money taxFor(Order order); }\n\n@Component @ConditionalOnProperty(name = \"acme.tax.region\", havingValue = \"BR\")\nclass BrazilTaxCalculator implements TaxCalculator { ... }\n\n@Component @ConditionalOnProperty(name = \"acme.tax.region\", havingValue = \"PT\")\nclass PortugalTaxCalculator implements TaxCalculator { ... }\n```\n\n**The condition that justifies it:** a concrete configuration-time variation or supported\nexternal extension contract. One bundled implementation can be enough for a public SPI whose\nproviders are deployed independently. A private switch with no such requirement may simply add\nwiring and misconfiguration costs; compare direct construction and preserve published contracts.\n\n**Costs even when justified:** the actual behaviour is not determinable from the code alone;\na misconfiguration fails at startup if you are lucky and at first use if you are not; and\nevery implementation needs its own tests plus a test that the selection works.\n\nFor this tax selector, reject an unknown region rather than silently changing tax rules.\nTest supported, missing and ambiguous selection against the declared contract, including any\nexplicit default, and identify provider initialization and cleanup ownership.\n\n### Extension compatibility and execution trust\n\nDistinguish approved application code selected at startup from arbitrary code supplied by a\ncustomer. The same interface can describe both, but it does not grant the same execution\nauthority. Before loading external providers, establish their provenance, allowed file/network\nand credential access, resource limits and failure containment. A separate class loader can\nhelp with class identity or dependency separation; that alone is not a security boundary.\n\nProvider creation is execution. With Java 17 `ServiceLoader`, iteration can instantiate a\nprovider through its constructor or provider method; `Provider.get()` also obtains an instance.\nDo not instantiate unfamiliar providers merely to inspect their declared capabilities.\nMetadata/type inspection and running provider code establish different evidence. See the\n[ServiceLoader contract](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/ServiceLoader.html).\n\nFor approved code, retain an adequate in-process selector and its compatibility, selection,\ninitialization and cleanup tests.
