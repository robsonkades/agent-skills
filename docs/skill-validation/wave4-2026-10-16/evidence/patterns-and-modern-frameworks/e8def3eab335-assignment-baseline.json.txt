Inspect its extension points before introducing a parallel dispatch mechanism.\n\n**What remains yours:** which concern goes at which stage of the chain\n(`mvc-and-request-handling`).\n\n**Wrapper to avoid:** a `BaseController` holding cross-cutting helpers. Every one of those\nconcerns should first be evaluated against filters, interceptors, resolvers and advice;\na domain-specific controller collaborator can still have a purpose.\n\n### Unit of Work → the persistence context\n\nChange tracking and synchronization of managed state. Flush is not commit; the transaction\nmanager controls commit, and a persistence context can flush multiple times.\n\n**The gap that matters:** context lifetime depends on creation and integration. A\ntransaction-scoped context follows the transaction; extended contexts, application-managed\ncontexts and Open Session In View can span multiple transactions. `REQUIRES_NEW` creates an\nindependent transaction when interception and the transaction manager support it; it does\nnot make the entire use case atomic. A detached entity is not tracked by a context.\n\n**Wrapper to avoid:** a hand-written \"unit of work\" collecting changes and applying them at\nthe end when the persistence context already owns that work. Competing change trackers can\ndisagree about flush order; a higher-level application transaction boundary is a different role.\n\n### Identity Map → the first-level cache\n\nOne managed instance per persistent entity identity within a context. Identity is not\nmerely a table row: inheritance and distinct entity mappings matter. A repeated `find`\nmay reuse a managed instance, while JPQL queries, refresh or lock modes can still issue SQL.\nShared identity does not make mutation or concurrent access safe.\n\n**The gap that matters:** this context-local cache is not a cross-context cache. Its lifetime\nis the context's, and an EntityManager is not safe for concurrent use. Bulk SQL may leave\nmanaged objects stale; explicitly refresh or clear with care for pending changes (`orm-behavioral-patterns`).\n\n**Wrapper to avoid:** a request-scoped map of loaded entities \"to avoid reloading\". Inside a\ncontext it usually duplicates identity management; outside one, detached data requires\nexplicit freshness and lazy-loading rules.\n\n### Lazy Load → ORM proxies\n\n**The gap that matters:** loading can be triggered by access, enhancement or provider behavior;\nloop traversal can cause N+1 selects, depending on distinct targets, caches and fetch plans. The pattern is provided; the **fetch strategy is a decision\nper use case** and the framework's default is not one.\n\n### Metadata Mapping → annotations and `orm.xml`\n\n**The gap that matters:** the metadata is not validated against the schema unless you ask —\nSpring Boot's `spring.jpa.hibernate.ddl-auto=validate` enables Hibernate schema validation.\nThat validation is not a complete audit of every constraint, index or migration\n(`metadata-mapping`).\n\n### Plugin → conditional bean registration\n\n`@ConditionalOnProperty` and profiles implement selection at configuration time.\n\n**The gap that matters:** define whether missing configuration selects a documented default\nor is an error. Validate required selections and ambiguous/missing beans at startup;\nconditional registration alone does not validate configuration or implement runtime hot loading.\n\n### Registry → the application context\n\nConstructor injection makes dependencies explicit; lifecycle and configuration costs remain. Used as\n`context.getBean()` inside business code, it is the classical Registry with all of them\n(`enterprise-base-patterns`).\n\n## Provided partially — mechanism yes, decision no\n\n### Repository → Spring Data\n\n**Provided:** the implementation, derived queries, paging, specifications.\n\n**Not provided, and it is the entire pattern:**\n\n- which aggregates exist and where their boundaries are;\n- whether repositories follow DDD aggregate roots when that model is used; Fowler's\n  collection-like interface to domain objects does not universally require a DDD root;\n- what the published surface is — `extends JpaRepository` publishes a broad inherited API including\n  `deleteAll()`;\n- whether reads for screens use the repository or a projection/query path;\n- that the interface speaks the domain's language.\n\n```java\n// Framework's answer — a complete implementation of nothing you decided.\ninterface OrderRepository extends JpaRepository<Order, Long> { }\n\n// Your decision: the surface, in your language, over one aggregate root.\npublic interface Orders {\n    Optional<Order> byId(OrderId id);\n    List<Order> overdueFor(CustomerId customer, LocalDate asOf);\n    Order save(Order order);\n    OrderId nextIdentity();\n}\n```\n\n**Wrapper to avoid:** an identical pass-through interface with no additional contract.\nCheck for an actual compatibility, lifetime, failure or application-owned replacement seam\nbefore calling it redundant. Narrowing is one justification; merely renaming adds no such\ncontract (`repository-pattern`).\n\n### Service Layer → `@Transactional`\n\n**Provided:** declarative demarcation, propagation, rollback rules.\n\n**Not provided:** what a use case is; where the boundary belongs; that it is demarcated once\nper use case; what happens at a non-transactional edge.\n\n**Gaps that cause incidents:** self-invocation bypasses new advice in default proxy mode,\nthough an existing outer transaction still applies; AspectJ weaving differs. Traditional\nrollback defaults exclude checked exceptions unless configured (including configurable\nglobal defaults in Spring 6.2+). Inherited CRUD methods have transaction metadata; declared\nquery methods do not automatically get it. An outer service transaction normally governs\nparticipating repository calls, so there is no universal transaction-per-query rule\n(`enterprise-transactions`).\n\n### Optimistic Offline Lock → `@Version`\n\n**Provided:** the version column, the `WHERE` clause, the exception.\n\n**Not provided:** returning the editor's original version (a fresh server read protects only\nsubsequent races, not earlier thinking-time edits); conflict presentation and valid retry.\nBulk statements need explicit version participation: incrementing invalidates old editors,\nwhile an expected-version predicate protects the bulk operation's own stale snapshot\n(`offline-concurrency-control`).\n\n### Data Mapper → JPA\n\n**Provided:** the mapping engine.\n\n**Not provided:** whether the domain model is allowed to diverge from the schema. Annotating\ndomain classes creates metadata coupling; it does not make those entities Active Record\nunless they also own persistence behavior. Record the chosen coupling and separation\n(`data-source-patterns`).\n\n### Caching → the caching abstraction\n\n**Provided:** `@Cacheable`, `@CacheEvict`, a pluggable store.\n\n**Not decided:** whether to cache, keys, TTL, size bounds, consistency and cross-instance\ninvalidation. `@Cacheable(sync=true)` requests synchronized loading from the provider with\nAPI restrictions; verify its actual scope, especially across nodes. Avoid sharing managed\nmutable entities as application-cache values without an explicit lifecycle contract\n(`caching-strategies`).\n\n**Gap that surprises:** default proxy-mode `@Cacheable` does not intercept same-bean calls;\nAspectJ mode has different interception semantics. Verify caching is enabled and the actual\ncache manager implements the intended behavior.\n\n**Composition gap:** `@CacheEvict` with the default `beforeInvocation=false` follows successful\nmethod invocation, not necessarily transaction commit. An outer transaction may roll back\nafter that method returns. Inspect the actual transaction boundary, advice order and cache\nmanager before claiming that annotation composition keeps cache publication consistent with\ndatabase commit. `beforeInvocation=true` deliberately evicts regardless of method outcome.\n\nWhen publication must follow successful commit, first inspect existing transaction-aware\ncache integration. Spring's `TransactionAwareCacheDecorator` defers `put`, `evict` and `clear`\nthrough active transaction synchronization; without it they execute immediately. Immediate\noperations such as `putIfAbsent`, `evictIfPresent` and `invalidate` are not deferred. Verify the\nactual operation and test successful commit and outer rollback. Keep an adequate integration;\ndo not add transaction machinery to a cache whose contract does not require it. This mechanism\nalone supplies neither atomic database/cache commit nor durable invalidation after a process\nfailure. For those requirements, pass the transaction topology, cache provider, stale-data\ntolerance and failure window to `caching-strategies` / `enterprise-transactions`; if unavailable,\nreport the missing guarantee and required recovery check rather than assert consistency.\n\nThese distinctions follow the [Spring 6.2.10 CacheEvict contract](https://github.com/spring-projects/spring-framework/blob/v6.2.10/spring-context/src/main/java/org/springframework/cache/annotation/CacheEvict.java)\nand [transaction-aware cache implementation](https://github.com/spring-projects/spring-framework/blob/v6.2.10/spring-context-support/src/main/java/org/springframework/cache/transaction/TransactionAwareCacheDecorator.java).\nThey are verification baselines; Virtual threads are final in Java 21. `JdbcClient` requires Spring Framework 6.1+;\nrecord embeddables require provider support (Hibernate 6.2+, standardized by Persistence\n3.2). Inspect the project's toolchain and resolved dependencies; do not upgrade implicitly.\n\n## Records: where they fit and where they do not\n\n| Use                            | Record?     | Why                                                                          |\n| ------------------------------ | ----------- | ---------------------------------------------------------------------------- |\n| Value Object (Money, TaxId)    | **Yes**     | Equality by value, immutability, validation in the compact constructor       |\n| Embedded Value (`@Embeddable`) | **Yes**     | Supported from Hibernate 6.2                                                 |\n| DTO / request / response       | **Yes**     | Shallow carrier; verify serializer names, annotations and wire compatibility |\n| Command                        | **Yes**     | Immutable input to a use case                                                |\n| Domain event                   | **Yes**     | A fact does not change                                                       |\n| Projection / row               | **Yes**     | Constructor expressions and interface-free projections                       |\n| Aggregate root                 | **Depends** | An immutable state model can use records; mutable JPA entities cannot        |\n| JPA `@Entity`                  | **No**      | Records do not satisfy entity class requirements                             |\n| Identity-bearing state         | **Depends** | Distinguish identity from record state equality and replacement semantics    |\n\nRecord support for an ordinary embedded value does not establish support for `@EmbeddedId`\nor `@IdClass`. The [Hibernate 6.2 introduction](https://docs.hibernate.org/orm/6.2/introduction/html_single/#embeddable-objects)\ndocuments record embeddables alongside an `@EmbeddedId` restriction dated May 2023;\n[Persistence 3.2, section 2.4.1](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2#composite-primary-keys)\nexplicitly permits record primary-key classes. Inspect the exact provider/update and mapping\nrole instead of extending either statement to every version. Before converting a key, verify\npersist/reload and lookup by key, including equality consistent with the mapped database types.\n\n```java\npublic record Money(BigDecimal amount, Currency currency) {\n\n    public Money {\n        Objects.requireNonNull(amount);\n        Objects.requireNonNull(currency);\n        int digits = currency.getDefaultFractionDigits();\n        if (digits < 0) throw new IllegalArgumentException(\"fraction digits undefined\");\n        amount = amount.setScale(digits, RoundingMode.UNNECESSARY);\n    }\n\n    public Money plus(Money other) {\n        requireSameCurrency(other);\n        return new Money(amount.add(other.amount), currency);\n    }\n\n    public boolean isLessThan(Money other) {\n        requireSameCurrency(other);\n        return amount.compareTo(other.amount) < 0;\n    }\n\n    private void requireSameCurrency(Money other) {\n        Objects.requireNonNull(other);\n        if (!currency.equals(other.currency)) throw new IllegalArgumentException(\"currency mismatch\");\n    }\n}\n```\n\nThis example uses the currency's default fractional digits as an explicit domain policy;\nsome pricing or settlement domains need another scale. Canonical scale makes record equality\nconsistent for amounts such as 1.0 and 1.00; excess nonzero precision is rejected, not rounded.\n\nThe compact constructor enforces this example's null/currency/scale policy, not every domain\nMoney invariant: a nonnegative-balance rule would need separate enforcement. Behaviour on the\ntype centralizes the currency checks required by these operations.\n\n**The trap:** a record component of a mutable type (`List`, `Map`, array, `Date`) is not\ndeeply immutable. Copy mutable containers on input/output, or use `List.copyOf` for an\nunmodifiable list; that copy is shallow and rejects null elements. Mutable elements need\nimmutable representations or deeper defensive copies. Array components also retain\nreference-based default record equality unless deliberately overridden.\n\n## Sealed types and exhaustive switch\n\nThe modern expression of a closed hierarchy — outcomes, states, instrument types:\n\n```java\npublic sealed interface SettlementResult {\n    record Settled(PaymentId payment, Instant at)      implements SettlementResult { }\n    record Rejected(RejectionReason reason)            implements SettlementResult { }\n    record Pending(Instant retryAfter)                 implements SettlementResult { }\n}\n\n// On recompilation, a newly uncovered variant makes this no-default switch incomplete.\nString describe(SettlementResult result) {\n    return switch (result) {\n        case SettlementResult.Settled(var payment, var at) -> \"settled by \" + payment + \" at \" + at;\n        case SettlementResult.Rejected(var reason)         -> \"rejected: \" + reason;\n        case SettlementResult.Pending(var retryAfter)      -> \"pending until \" + retryAfter;\n    };\n}\n```\n\n**Where this replaces a classical pattern:**\n\n- **Special Case** where callers must distinguish — a sealed variant plus exhaustive switch\n  is better than an `instanceof` check against a null object.\n- **Result/outcome types** instead of exceptions for expected business outcomes: the outcome\n  is in the signature; callers can still ignore returned values, so API usage needs review.\n- **State machines** in the domain, with transitions as methods returning the next state.\n\n**Where it does not replace a pattern:** Plugin discovery and lifecycle still need a mechanism.\nA sealed root prevents arbitrary new direct implementations, but it can deliberately permit\nan open extension branch. For example, this Java 17+ API keeps the built-in case closed while\nallowing third-party implementations of `Handler.Extension`:\n\n```java\npublic sealed interface Handler permits Handler.BuiltIn, Handler.Extension {\n    record BuiltIn() implements Handler { }\n    non-sealed interface Extension extends Handler { }\n}\n```\n\nKeep that branch accessible to plugin code (and export its package when using named modules).\nA Java 21 switch covering `BuiltIn` and `Extension` is exhaustive for these branches, even\nwhen another plugin later implements `Extension`. It does not force a separate case for every\nplugin class. Choose an open root when arbitrary direct implementations are required; retain\na sealed root with an open branch when that is the intended contract (`enterprise-base-patterns`).\nThe [Java 21 sealed-type rules](https://docs.oracle.com/javase/specs/jls/se21/html/jls-9.html#jls-9.1.1.4)\ndistinguish a closed set of direct subtypes from a freely extensible `non-sealed` subinterface.\n\nOmit `default` when requiring each variant to be handled after recompilation. A deliberate\nfallback can be appropriate for compatibility, but loses that diagnostic. Separately compiled\nclients are not retroactively checked and may throw `MatchException` on a new unmatched\nvariant. A null selector needs `case null` or an explicit non-null precondition.\n\n## Immutability against JPA's requirements\n\nJPA entity classes require an accessible no-arg constructor and a supported field or\nproperty access strategy. Field access does not require public setters; property access\nhas accessor requirements. Persistent fields must not be final for portable entities:\n\n```java\n@Entity\npublic class Order {\n\n    @Id private Long id; // typed domain identifiers need a supported identifier mapping\n    private Long customerId;\n    @Enumerated(STRING) private OrderStatus status;\n    @OneToMany(mappedBy = \"order\", cascade = ALL, orphanRemoval = true)\n    private List<OrderLine> lines = new ArrayList<>();\n    @Version private long version;\n\n    protected Order() { }                     // for the ORM only; not public\n\n    public Order(Long id, Long customerId) {   // enforces the invariants\n        this.id = Objects.requireNonNull(id);\n        this.customerId = Objects.requireNonNull(customerId);\n        this.status = OrderStatus.DRAFT;\n    }\n\n    public void confirm(Money creditLimit) {  // a transition, not a setter\n        requireDraft();\n        if (creditLimit.isLessThan(total())) throw new CreditLimitExceeded(id, creditLimit);\n        status = OrderStatus.CONFIRMED;\n    }\n\n    public List<OrderLine> lines() { return List.copyOf(lines); } // protects list structure only\n}\n```\n\nA protected constructor and domain transitions allow a rich JPA entity. The returned list\nstill exposes child references: restrict child mutators or return immutable projections if\ncallers must not mutate them. This addresses the setter objection; a separate domain model\ncan still be justified by lifecycle, boundary or persistence independence requirements\n(`data-source-patterns`).\n\n## Optional at boundaries, not in fields\n\n```java\npublic interface Orders {\n    Optional<Order> byId(OrderId id);       // signals absence; callers can still ignore the result\n}\n\n@Entity\npublic class Order {\n    private Instant cancelledAt; // Optional<Instant> is not a standard JPA basic mapping\n    public Optional<Instant> cancelledAt() { return Optional.ofNullable(cancelledAt); }\n}\n```\n\nUse Optional primarily for return values signaling absence; fields and parameters are API\ndesign choices, not forbidden Java syntax. Avoid assuming portable JPA persistence or\nserialization support for Optional. A Special Case is useful only when absence has genuine\nuniform domain behavior (`enterprise-base-patterns`).\nThe return type expresses intent; it does not enforce caller handling. Review use sites\nwhere dropping the result would violate the operation's contract.\n\n## Virtual threads and the patterns\n\nVirtual threads change the **sizing arithmetic**, not the patterns:\n\n- **Blocking thread-per-task becomes a viable option for I/O-heavy work.** Streaming,\n  backpressure, framework integration and existing code can still justify reactive pipelines\n  (`reactive-and-virtual-thread-selection`).\n- **Connection pools do not scale with threads.** If ten thousand tasks simultaneously\n  request one connection each from a saturated pool of 20, up to 9 980 must wait or be rejected.\n  The pool is still the bound, and connection hold duration\n  still sizes it (`connection-pool-sizing`).\n- **Imperative Spring transactions normally use thread-bound resources.** Starting another\n  thread does not propagate that transaction; an EntityManager must not be used concurrently.\n  A proxy might still reference an open context, which makes cross-thread access unsafe rather\n  than automatically detached.
