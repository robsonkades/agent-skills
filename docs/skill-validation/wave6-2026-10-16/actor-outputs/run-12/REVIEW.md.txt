O contrato está **violado** em `src/work/Job.java:8`: `join(2)` pode devolver o controle por timeout, mas `collect()` sempre lê `result` e anuncia `DONE`. O contrato permite `PENDING` durante a execução e proíbe `DONE:0`.

O caminho efetivo é: construir `Job` → iniciar essa mesma thread uma vez → `run()` aguardar o gate → escrever `result=83` → terminar. Em paralelo, `collect()` espera no máximo os 2 ms configurados, mais custos de agendamento, e lê o campo mesmo se a thread continuar viva. O prazo não é evidência de conclusão. A [API Java SE25 de Thread.join(long)](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.html#join(long)) especifica espera limitada; esse overload não retorna um indicador de término.

`result` tem inicialização padrão em zero, uma escrita ordinária em `run()` e leituras ordinárias em `collect()`. Sua atomicidade como `int` não comprova conclusão. A inicialização anterior a `start()` é publicada para o worker; a referência `final gate` não publica a escrita posterior de `result`. Nos caminhos em que a espera expira, falta a detecção de término que ordenaria a escrita com a leitura; em usos concorrentes gerais elas podem ficar sem ordenação.

Correção mínima proposta, **não aplicada**:

```java
public String collect() throws InterruptedException {
    join(2);
    if (isAlive()) return "PENDING";
    return "DONE:" + result;
}
```

A consulta é feita na própria thread iniciada. Sob o ciclo de vida aceito, `isAlive()==false` detecta seu término. A prova é: escrita `result=83` → ordem de programa → ação final do worker → synchronizes-with → detecção de término → ordem de programa → leitura de `result`. A transitividade estabelece happens-before; não há escrita posterior. Essa garantia vem da [JLS 17.4.4–17.4.5, SE25](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html#jls-17.4.4), independentemente do processador ou JIT. O retorno `PENDING` evita a leitura durante a execução, preservando a espera limitada. Tornar apenas `result` volatile ainda permitiria anunciar zero antes do trabalho.

A proposta preserva a propagação de `InterruptedException` da coleta. A interrupção do worker pode fazê-lo terminar sem escrever 83; término não significa sucesso em contratos com cancelamento, explicitamente fora deste pedido. A prova usa o ciclo de vida aceito, após `start()`; um objeto nunca iniciado não seria comprovadamente concluído por `isAlive()==false`.
