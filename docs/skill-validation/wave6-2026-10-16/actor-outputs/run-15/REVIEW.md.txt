# ResultBridge.currentValue(): unresolved production guarantee

The accepted contract permits `-1` when no snapshot is available and requires `91` for a present snapshot. **Disposition: unresolved.** The available provider contract does not establish the producer-to-callback publication needed to prove the production guarantee. No production failure was observed; the deployed provider was unavailable.

In `src/work/ResultBridge.java:4`, the callback assigns its argument to volatile `latest`. Line 5 reads that reference once, returns `-1` for null, otherwise reads `Snapshot.value`. In `Snapshot.java:2`, that value is an ordinary mutable `int`, assigned by a setter; declaring the class final does not make the field final. The accepted prohibition on mutations after handoff is sufficient for stability once initialization is safely published.

The required chain is:

```text
producer: setValue(91)
    -- same-thread program order OR an established cross-thread handoff -->
callback: volatile latest = snapshot
    -- volatile synchronization -->
reader: observed = latest; observed.value()
```

Java SE 25 establishes program-order edges, volatile-write-to-subsequent-read synchronization, and transitivity. Consequently, the bridge safely conveys initialization that already happens-before its volatile assignment. It does not create a missing upstream edge merely by republishing a reference. Wall-clock precedence alone is insufficient. With an unsynchronized producer-to-callback handoff, a stale default value is not excluded; that conditional case is not a finding about the absent provider. [JLS 17.4.4–17.4.5](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html#jls-17.4.5)

The synchronous fixture in `test/work/Smoke.java:4` constructs, initializes and delivers the snapshot on the calling thread, then reads the bridge on that same thread. Its initialization/read ordering is established even without testing cross-thread visibility. A provider that initializes and invokes the callback on one producer thread would also have the needed upstream ordering; a different callback thread can be valid with a documented safe handoff. Neither arrangement can be inferred for production from the supplied interface, callback count or timing log.

The smallest evidence needed is the actual provider path (source/binary analysis or a verifiable threading and synchronization specification) identifying the `setValue(91)` action, callback thread and intervening happens-before edges. Alternatively, add a binding provider memory-consistency clause: **the write establishing value 91, and all required snapshot initialization, happen-before invocation of the callback with that snapshot.** Retain the already accepted no-later-mutations rule and obtain evidence that the deployed provider conforms. The existing bridge then needs no change. No production source correction is justified without that integration evidence; adding another downstream volatile write or callback-only lock would not establish the missing upstream relationship.
