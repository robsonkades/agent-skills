Disposition: **violated**.

The accepted contract requires construction-time values to survive producer-buffer recycling. In `src/work/Message.java:4`, `this.words=words` retains the producer's array. `checksum()` on line 5 reads that same array on every call. The private final reference and absence of a public mutator do not remove this external writable alias.

The provided `Smoke` follows the accepted lifecycle: initialize `{10,20}`, construct a message, calculate its checksum, recycle the buffer to `{100,200}`, then calculate again. Program order alone establishes this counterexample; concurrency is unnecessary. The required result is 30 both times, but the supplied implementation yields 300 after recycling.

For initialization, the constructor assigns the final reference without exposing `this`. Its exit freezes that field; initialization writes ordered before the freeze can receive the special final-field protection when a consumer dereferences it. That protection neither freezes array elements nor orders later producer writes with consumer reads, and it is not a general publication happens-before edge. [JLS 25 §§17.5–17.5.1](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html#jls-17.5.1)

With concurrent recycling, conflicting ordinary reads/writes of `words[0]` and `words[1]` lack a supplied ordering protocol. Each int access is atomic, but their sum is not a snapshot. For the example, ordinary interleavings can produce 120 or 210 as well as 30 or 300. Those are implementation-permitted outcomes, while the contract accepts only 30. [JLS 25 §§17.4–17.4.5](https://docs.oracle.com/javase/specs/jls/se25/html/jls-17.html#jls-17.4.5)

The minimal adequate correction is to retain the existing null/length guard and replace only the assignment with `this.words = words.clone();`. This is a proposal, not an applied change. Under the accepted lifecycle, recycling starts after construction returns, so the copy captures both input words before recycling. An ordinary primitive array copy removes the producer alias; the private copy is neither exposed nor subsequently mutated. Keeping the final field preserves construction-time visibility, and checksum remains read-only. A volatile reference or synchronization confined to `checksum()` would still permit the sequential counterexample. Requiring callers to retain buffers would contradict the contract.
