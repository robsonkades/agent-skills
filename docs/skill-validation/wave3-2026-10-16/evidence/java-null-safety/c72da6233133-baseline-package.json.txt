Each public type belongs in its own file. The before sketch assumes a map\nthat accepts null keys; other stores may reject earlier. Domain constructors provide runtime\nchecks; annotations describe the static contract, not enforcement by themselves.\n\n## Before\n\n```java\npublic record InvoiceLineDto(String sku, BigDecimal amount) {}\npublic record InvoiceDto(String id, String customerId,\n                         List<InvoiceLineDto> lines, Instant issuedAt) {}\n\npublic class InvoiceService {\n    public void register(InvoiceDto dto) {\n        store.put(dto.id(), dto);                    // dto.id() may be null\n    }\n    public List<InvoiceLineDto> linesFor(String invoiceId) {\n        InvoiceDto invoice = store.get(invoiceId);\n        return invoice != null ? invoice.lines() : null;   // null for two reasons\n    }\n}\n\npublic class TotalsService {\n    public BigDecimal total(String invoiceId) {\n        BigDecimal sum = BigDecimal.ZERO;\n        for (InvoiceLineDto line : invoiceService.linesFor(invoiceId)) {  // NPE here\n            sum = sum.add(line.amount());            // line.amount() may also be null\n        }\n        return sum;\n    }\n}\n```\n\n## Analysis\n\nThree distinct nulls are conflated, and none has a stated meaning:\n\n1. **Error null.** `dto.id()` null means the payload was invalid — but it is accepted,\n   stored under a null key, and the failure surfaces later as a lookup miss or an NPE.\n   The assumed binder/store path permits this; actual missing/null handling depends on mapper\n   configuration. JSpecify annotations alone would not have stopped it.\n2. **Absence null, doubled.** `linesFor` returns null both for \"unknown invoice\" and for\n   \"invoice with a null lines field\" — the caller cannot distinguish them and forgot to\n   check either.\n3. **Leaked nullable element.** `line.amount()` came from the wire unvalidated and is\n   dereferenced in arithmetic far from the boundary.\n\nThe defect is not the missing `!= null` in `TotalsService` — adding it there would be a\nfourth scattered check. The defect is that no boundary converts wire-shaped data into\ncontract-carrying data.\n\n## After\n\nModel the raw DTOs explicitly, then convert at the adapter. Domain constructors enforce their\nown runtime contract:\n\n```java\n@NullMarked\npublic record InvoiceLineDto(@Nullable String sku, @Nullable BigDecimal amount) {}\n\n@NullMarked\npublic record InvoiceDto(@Nullable String id, @Nullable String customerId,\n                         @Nullable List<@Nullable InvoiceLineDto> lines,\n                         @Nullable Instant issuedAt) {}\n\n@NullMarked\npublic record InvoiceLine(String sku, BigDecimal amount) {\n    public InvoiceLine {\n        Objects.requireNonNull(sku, \"sku\");\n        Objects.requireNonNull(amount, \"amount\");\n    }\n}\n\n@NullMarked\npublic record Invoice(String id, String customerId,\n                      List<InvoiceLine> lines, Instant issuedAt) {\n    public Invoice {\n        Objects.requireNonNull(id, \"id\");\n        Objects.requireNonNull(customerId, \"customerId\");\n        Objects.requireNonNull(issuedAt, \"issuedAt\");\n        lines = List.copyOf(lines);       // rejects null list and null elements\n    }\n}\n\nfinal class InvalidInvoicePayload extends IllegalArgumentException {\n    private final String field;\n    private final String code;\n\n    InvalidInvoicePayload(String field, String code) {\n        super(field + \": \" + code);\n        this.field = field;\n        this.code = code;\n    }\n\n    String field() { return field; }\n    String code() { return code; }\n}\n\n// The following mapper methods live in the inbound adapter.\n@NullMarked\nstatic <T> T required(@Nullable T value, String field) {\n    if (value == null) throw new InvalidInvoicePayload(field, \"required\");\n    return value;\n}\n\n@NullMarked\nstatic Invoice fromDto(@Nullable InvoiceDto dto) { // nullable body is rejected explicitly\n    if (dto == null) throw new InvalidInvoicePayload(\"body\", \"required\");\n    String id = required(dto.id(), \"id\");\n    String customerId = required(dto.customerId(), \"customerId\");\n    Instant issuedAt = required(dto.issuedAt(), \"issuedAt\");\n    List<@Nullable InvoiceLineDto> rawLines = required(dto.lines(), \"lines\");\n    List<InvoiceLine> lines = IntStream.range(0, rawLines.size())\n        .mapToObj(i -> {\n            InvoiceLineDto line = required(rawLines.get(i), \"lines[\" + i + \"]\");\n            return new InvoiceLine(\n                required(line.sku(), \"lines[\" + i + \"].sku\"),\n                required(line.amount(), \"lines[\" + i + \"].amount\"));\n        })\n        .toList();\n    return new Invoice(id, customerId, lines, issuedAt);\n}\n\npublic Optional<Invoice> findInvoice(String invoiceId) {\n    return Optional.ofNullable(store.get(Objects.requireNonNull(invoiceId, \"invoiceId\")));\n}\n```\n\n`InvalidInvoicePayload` and `required` are boundary helpers that expose stable field/code data and\ndo not echo sensitive values. `TotalsService.total(Invoice)` now receives a proven domain object;\nits caller handles `findInvoice` absence explicitly. An existing invoice with no lines legitimately\ntotals zero, while an unknown invoice does not silently become one. Optional mechanics belong to\njava-optional.\n\n`required(dto.lines(), \"lines\")` establishes that the list reference is non-null; it does not\nvalidate its elements. Keep `rawLines` as `List<@Nullable InvoiceLineDto>` until each element\npasses its own `required` check. The mapper methods are null-marked here; an enclosing\nnull-marked adapter is another option. Leaving DTOs unmarked instead creates an\nunspecified/unchecked boundary. Test the actual\nmapper's missing-field/null behavior and map `InvalidInvoicePayload` to the intended HTTP\nresponse; a Java exception alone does not establish a 4xx response. A non-null `Invoice`\nreference is still a separate precondition of the downstream total method.\n\n## Trade-offs\n\n- Invalid payloads now fail at ingestion with a stable field/code exception; an exercised HTTP\n  exception mapping is still needed to establish a 4xx response. Rejection instead of storing\n  invalid data is a behaviour change that must be flagged, not smuggled in. Clients\n  that depended on lenient acceptance will notice.\n- A DTO-to-domain conversion layer is real code: one more type per aggregate, one mapping\n  function, kept in sync. For a two-endpoint service this can be ceremony; the trade pays\n  off when multiple call paths consume the same data, which is exactly when scattered\n  checks fail.\n- `requireNonNull` inside the record re-checks what `fromDto` established. Constructors\n  keep their checks anyway — the record is also constructible without the adapter, and\n  its contract must not depend on one caller's diligence. This is the one place\n  double-checking is by design.\n\n## Verification\n\nAcceptance checks to execute in the target build; no checker or HTTP result is implied by these sketches:\n\n- Tests feeding a DTO with each required field null: rejected at `fromDto` with a message\n  naming the payload problem — not an NPE from deeper in.\n- A test for the unknown-invoice path asserting `Optional.empty`, distinct from an invoice whose\n  line list is empty and total is zero.\n- Run the configured checker over the marked domain and adapter, with compile fixtures for\n  null DTO fields, null line elements and invalid overrides. Include a negative fixture that\n  assigns the validated list reference to `List<InvoiceLineDto>` before validating its elements;\n  checking the outer reference must not erase nested nullability. Record warnings and unchecked\n  scopes; do not report success merely because the domain is marked or DTOs are unmarked.\n- Re-run the production NPE path as a regression; assert stable field/code and no store write\n  for invalid input, plus direct constructor rejection when the adapter is bypassed.\n\n## Authoritative references\n\n- [Objects.requireNonNull API, Java SE 25](<https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Objects.html#requireNonNull(T,java.lang.String)>)\n- [Optional API, Java SE 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Optional.html)\n- [JSpecify generic element and container nullness](https://jspecify.dev/docs/user-guide/#generics)\n- [List.copyOf null rejection, Java SE 25](<https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html#copyOf(java.util.Collection)>)\n"

Support depth still varies—especially for generic inference, wildcards, JDK\nmodels and bytecode type annotations—so “uses JSpecify” does not prove equivalent enforcement.\nTwo annotations carry the core contract:\n\n- `@NullMarked` — establishes null-marked scope on a module, package (`package-info.java`),\n  class or method. Ordinary concrete reference types default to non-null, but type variables\n  may carry parametric nullness and local root types are inferred. A marked package does not\n  mark its subpackages; `@NullUnmarked` opts a nested scope back into unspecified nullness.\n- `@Nullable` — a type-use annotation marking the exceptions: `@Nullable Customer\nfindBy(String id)` says \"null is a legal return and means something\".\n\n```java\n// package-info.java\n@NullMarked\npackage com.example.billing;\n\nimport org.jspecify.annotations.NullMarked;\n```\n\nWhat this buys, precisely: a machine-readable contract that compatible tools may check at build,\nedit or interop time. What it\ndoes not buy: built-in runtime enforcement. With ordinary `javac` and no generated validation,\nan annotated method can still return null. Runtime consumers can read retained annotations;\ncredit enforcement only to an identified checker or validation path actually exercised.\nDocumentation/interop benefits and a configured CI check are different outcomes; say which exists.\n\n## Adoption strategy for an existing codebase\n\n1. When adoption is in scope, add a pinned `org.jspecify:jspecify` annotation dependency and\n   checker/compiler configuration. Preserve annotations for published consumers; check dependency\n   exposure and bytecode/module metadata rather than assuming local source analysis covers them.\n2. `@NullMarked` one coherent package at a time, often starting with dependency-leaf value/core\n   APIs where contracts are clearest. Boundary DTO packages may intentionally contain many legal\n   nulls and need explicit modelling before marking.\n3. In each package, the checker's findings sort into: real defects (fix), legal nulls\n   (mark `@Nullable` and make callers handle them), and boundary leaks (normalise at the\n   edge — below).\n4. Track a ratchet/baseline during migration and promote completed scopes to errors. Warning-only\n   findings need ownership and a burn-down gate or they tend to become background noise.\n\nFrameworks and dependencies may require other annotation vocabularies. Define which tool interprets\nwhich annotations/defaults, prevent contradictory duplicates on one type use, and migrate public\nsignatures deliberately; a blind mechanical replacement can change generic/array annotation\npositions and Kotlin semantics.\n\nUnmarked does not mean nullable: it means unspecified nullness. Annotate nullable DTO\ncomponents and nested elements explicitly when they are intended to be modeled by the checker;\notherwise record the boundary as unchecked. A module-wide `@NullMarked` also covers DTO packages\nunless an applicable `@NullUnmarked` scope overrides it.\n\n## Boundary tactics — where null leaks in regardless of contracts\n\n| Leak                     | Behaviour                                                                                         | Tactic                                                                                                                             |\n| ------------------------ | ------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |\n| JSON/XML deserialisation | missing/null handling depends on mapper/creator configuration and primitive versus reference type | test the configured binder, validate raw input and construct the domain contract                                                   |\n| ORM / JPA relations      | absent optional to-one may be null; lazy state is normally proxy/wrapper/provider-managed         | derive contract from mapping/schema/provider; do not label “unfetched” as null                                                     |\n| `Map.get`                | null for absent **and** for mapped-to-null                                                        | `getOrDefault` distinguishes absence but preserves an explicit null; `containsKey` distinguishes in a stable map; CHM forbids null |\n| Reference arrays         | every slot null-initialised                                                                       | track fill state or validate all slots; primitive arrays instead contain zero values                                               |\n| Legacy/third-party APIs  | unannotated returns                                                                               | wrap once in an adapter that establishes your contract; do not sprinkle checks at every call site                                  |\n\nThe shape is: establish the nullness contract where data enters/objects are constructed, then rely\non it within the checked scope. Re-check only when another framework, override, reflective path or\ntrust boundary can invalidate the proof.\n\n## Implicit unboxing can erase a legal absence\n\nUnboxing a null wrapper throws NPE. Numeric conditional expressions can unbox before assignment\nto a boxed result: `useDefault ? 3 : configured` has type `int` when `configured` is `Integer`.\nAnnotating the result nullable does not alter this language rule.\n\nThese partial Java method snippets belong in a null-marked class with the JSpecify 1.0\n`Nullable` import. Here null means “inherit the enclosing policy,” distinct from zero retries:\n\n```java\n// Before: configured == null throws when useDefault is false.\nstatic @Nullable Integer retryLimit(boolean useDefault, @Nullable Integer configured) {\n    return useDefault ? 3 : configured;\n}\n\n// After: explicit branches preserve the documented absence.\nstatic @Nullable Integer retryLimitPreservingAbsence(\n        boolean useDefault, @Nullable Integer configured) {\n    if (useDefault) return 3;\n    return configured;\n}\n```\n\nIf the receiving operation instead requires a primitive, resolve absence there: reject a missing\nrequired value or apply its specified default before unboxing. Do not preserve null into that\noperation, silently use zero, or add Optional merely to rewrite this expression. For a nullable\nBoolean, treating null as false is likewise a policy choice, not a universally safe correction.\n\nExercise both branches with null, zero and a nonzero value; assert whether absence is preserved,\ndefaulted or rejected. A configured checker should also flag the unsafe expression; plain\n`javac` compilation only verifies syntax/types. The mechanism is defined by\n[JLS 25 unboxing](https://docs.oracle.com/javase/specs/jls/se25/html/jls-5.html#jls-5.1.8) and\n[numeric conditional expressions](https://docs.oracle.com/javase/specs/jls/se25/html/jls-15.html#jls-15.25.2),\nchecked **2026-09-27**.\n\n## False positives — nullable that is not a defect\n\n- **A `@Nullable` field with a checked lifecycle.** A field null between construction and\n  a framework-driven `init()`, or until a state machine reaches the state that sets it,\n  is a documented phase, not a bug — provided every read either follows the lifecycle or\n  checks. Flag missing initialization, reset or publication rules when an allowed read can\n  observe an invalid state.\n- **Null as absence inside a private scope.** A local `Customer c = cache.get(id);`\n  checked before use can be adequate when it captures the intended lookup result. Line proximity\n  alone is not proof: callbacks or another writer can invalidate a field between check and re-read.\n  A non-null local does not prove that the referenced resource stays open or its state stays valid.\n- **A lazily computed cache field.** Null can legitimately mean \"not computed yet\"; it is not by\n  itself a safe single-check protocol. Establish confinement or the actual initialization and\n  publication contract — java-immutability covers derived-cache conditions and their limits.\n- **requireNonNull \"missing\" on a private method.** If every caller is inside the\n  boundary that already validated, the check is redundant by design. The finding is real\n  when an allowed call or intervening mutation can violate the precondition. Private visibility\n  alone proves neither valid input nor a stable lifecycle; an equivalent natural failure can\n  satisfy a public contract without a duplicate explicit check.\n\nThe inverse false negative is worth naming too: `requireNonNull` immediately before the same natural\ndereference may mainly improve blame location/message and stabilize the public failure point. That\ncan be valuable, but it is not runtime null-safety for later producers.\n\n## Tooling decision checks\n\n- Pin checker, plugin, `javac` and JSpecify versions; test upgrades on representative generics.\n- Compile published annotations into a consumer fixture, including Kotlin if supported.\n- Test override variance, arrays/varargs, `T extends @Nullable Object`, wildcards and unannotated\n  libraries—the places where checker support differs.\n- Count suppressions/baseline growth and require a reason/owner; “zero reported findings” is only as\n  strong as the analyzed scope and library models.\n\n## Authoritative references\n\n- [JSpecify 1.0 user guide](https://jspecify.dev/docs/user-guide/)\n- [JSpecify specification](https://jspecify.dev/docs/spec/)\n- [NullAway JSpecify support and limitations](https://github.com/uber/NullAway/wiki/JSpecify-Support)\n- [Map API null/getOrDefault contracts, Java SE 25](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Map.html)\n"
