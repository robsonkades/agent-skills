## Evidence and reasoning

- `protocol.json` sets `first_message` to `client`.
- `client.mjs` sends `PING\n` on its `connect` event for that selection.
- `server.mjs` waits for PING and ends with `PONG\n`. It sends an initial HELLO
  only for the alternative server-first selection.
- `adapter-contract.md` says `first_client_data` opens the upstream when client
  bytes arrive, and `immediate` opens it on downstream acceptance. The trusted
  route is known without payload parsing.
- Therefore the selected client can supply the bytes that release deferred
  connection. A server-first control exposes the opposite dependency, but does
  not justify changing this client-first policy.
- The only pre-review observation was TCP connect success. The additional
  observations below come from a local contract model, not the installed adapter.

The corrected decision records the loopback listener, fixed route, application
and adapter responsibilities, no-retry attempt bound, missing end-to-end deadline
evidence, failure checks and future rollback/connection-lifecycle limits.

## Executed local verification

Added `verify-handshake.mjs`, which imports the supplied client/server functions
without editing them. It models the two connection-start behaviors described
in the contract using Node TCP sockets on ephemeral `127.0.0.1` ports. The fixed
route maps solely to an ephemeral local fixture server. It does not bind the
configured port 15001 or connect to a real service.

The selected case loads both JSON files. Control cases change their parameters
only in memory. The check asserts exact protocol bytes, completion count,
upstream attempt/accept count and whether first client bytes precede upstream
connection creation. It preserves the 1,000 ms inspection bound and 4,096-byte
preconnection buffer bound. A three-second case deadline and fifteen-second
whole-process guard bound the run. All sockets are destroyed and listeners
closed in case cleanup; timers are cleared.

## Coverage limits

No adapter implementation, image/version or deployment is supplied. The model
tests handshake dependency and actual fixture application completion through
local sockets; it does not certify a real proxy. Timeout closure is the model's
chosen bounded failure signal, not an observed installed-adapter behavior.

The run does not validate production latency/load, buffer overflow, slow or
fragmented traffic, upstream refusal/stall, missing route, caller cancellation,
real deadline propagation, TLS/authentication, config reload/rollback or existing
long-lived connection migration. The 4,096-byte bound is modeled but not reached
by these small messages. The three-second test deadline is not a newly proposed
application deadline. No ten-second timeout experiment was run or needed to
infer that a timer alone cannot create the missing first message.

Before deployment, repeat the selected exchange and relevant bounded fault
checks through the real adapter, verify the fixed route and error/deadline
behavior, and establish its update/lifecycle contract. No executable vendor
configuration or deployment approval was produced. No tools were installed,
no retries introduced, and no TLS/authentication settings changed. Repository
build/test commands were not run: this task confines access to the isolated
fixture directory.
