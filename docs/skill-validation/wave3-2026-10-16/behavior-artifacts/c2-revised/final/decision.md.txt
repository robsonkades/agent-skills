# Proposal

Keep `proxy-policy.json` unchanged, including `connect_start=first_client_data`,
the 1,000 ms inspection timeout and the 4,096-byte buffer bound. `protocol.json`
selects a client-first exchange: `client.mjs` sends `PING\n` on TCP connect, and
`server.mjs` replies with `PONG\n`. Under `adapter-contract.md`, those first client
bytes trigger the upstream connection. This handshake has no circular wait that
requires switching to immediate connection.

The local contract is an explicit TCP connection to `127.0.0.1:15001`, followed
by forwarding to the trusted fixed route `fixed-service-a`. The adapter owns
connection timing and the fixed per-connection route; the application owns the
PING/PONG exchange. No payload-derived destination, HTTP authority mapping, TLS
termination change, authentication change or retry is proposed. One logical
exchange permits at most one upstream connection attempt in this proposal.

The previously reported TCP connect success establishes only that a listener
accepted a connection. It does not establish upstream connection creation or
PING/PONG completion. Remove the recommendation to increase the inspection
timeout to ten seconds: no observed stall or evidence of an inadequate 1,000 ms
bound is supplied. A server-first client would wait for `HELLO\n` while deferred
connection waits for client data; a longer timeout would prolong that circular
wait, not repair it. That counterexample is a control, not the selected protocol.

Run `node verify-handshake.mjs` for a bounded local check using the supplied
client/server functions and a small model of the written adapter contract.
The model uses ephemeral loopback ports, not the configured port or a deployed
proxy. Check actual PONG completion, byte order and upstream connection counts
for the selected client-first/deferred pair, plus both connection modes with
client-first and server-first controls. See `REVIEW.md` and retained `logs/` for
the actual execution results and limits.

The inspection timeout is not an end-to-end application deadline. The fixture
does not establish upstream connect/response deadlines, deadline propagation,
the adapter's exact timeout/error signaling, or its process lifecycle. Before
deployment, verify those bounds and failure behavior on the actual adapter
version: unavailable listener, absent route, upstream refusal/stall and caller
cancellation must not produce indefinite waits, retries or an unauthorized
bypass. No deployment approval follows from this review.

There is no policy rollout or rollback in this correction. A future policy
change needs the actual update mechanism and a tested last-good rollback.
Existing TCP connections retain their route unless a separately verified
drain/reconnect contract says otherwise; configuration acceptance alone does
not demonstrate their migration. Confirm the selected handshake through the
real adapter before treating protocol compatibility as established there.
