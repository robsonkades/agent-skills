# Review

Corrected `decision.md` and changed only `proxy-policy.json`'s `connect_start`
from `first_client_data` to `immediate`. The existing listener, fixed route,
1000 ms inspection bound and 4096-byte buffer limit remain unchanged.

The supplied sources establish a server-first exchange: `protocol.json` selects
`server`; `client.mjs` waits for `HELLO\n` before sending `PING\n`; `server.mjs`
sends the greeting on connection and responds with `PONG\n`. The adapter
contract says deferred mode opens no upstream until client bytes arrive, while
immediate mode can use the trusted fixed route at downstream acceptance.
Deferring therefore creates a circular wait. TCP connection success alone does
not establish handshake compatibility, and increasing the inspection timeout
does not create either missing first message.

Applied the supplied `ambassador-pattern` skill and its connection-establishment
guidance. Kept the review at the fixture contract level: no vendor configuration,
deployment, tool installation, retries, authentication or TLS change was made.
No implementation fixture was edited. Baseline SHA-256 values and the original
policy/decision are retained in `fixture-baseline.json`.

**Executed local verification**

Added `verify-handshake.mjs`, using Node built-ins and importing the original
`attachClient`/`attachServer` functions. It models the adapter contract on
ephemeral `127.0.0.1` ports; it never binds the policy's port 15001. Each case
has a 2500 ms guard, with a 12000 ms whole-run watchdog. The existing 1000 ms
inspection bound and 4096-byte buffer bound are used in the model. The
client-first control changes only an in-memory protocol object. There are no
retries, external network calls or child processes.

| Protocol / connection mode | Observed outcome | Upstream attempts / accepts | Bytes observed by client | Elapsed case time |
| --- | --- | --- | --- | --- |
| Server-first / deferred | TCP connected; no handshake; inspection expired | 0 / 0 | none | 1031.05 ms |
| Server-first / immediate | handshake completed | 1 / 1 | `HELLO\nPONG\n` | 3.36 ms |
| Client-first / deferred | handshake completed | 1 / 1 | `PONG\n` | 2.46 ms |
| Client-first / immediate | handshake completed | 1 / 1 | `PONG\n` | 1.97 ms |

Each successful upstream received exactly `PING\n`. All cases accepted exactly
one downstream connection; no socket errors occurred. The stalled case recorded
no downstream bytes and no upstream dial, distinguishing the wait from a
connection refusal. The successful server-first case recorded upstream creation,
server acceptance, `HELLO` arriving at the client, then `PING`, then `PONG` and
completion, in that order. These are local observations, not production latency
measurements.

adapter itself. No proxy executable/image/version or deployment configuration
was supplied. Closing the downstream on inspection expiry is the model's
bounded failure action; the contract does not specify the real adapter's exact
expiry response. The observations establish the fixture's first-message
ordering consequence without proving vendor compatibility.
