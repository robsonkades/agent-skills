# Proposal

Use `connect_start: "immediate"` for this server-first fixture. This is the only
policy field that needs changing. Preserve the loopback listener
`127.0.0.1:15001`, trusted `fixed-service-a` route, 1000 ms inspection timeout and
4096-byte inspection buffer limit.

`protocol.json` specifies a server-first protocol. In `client.mjs`, the client
waits for `HELLO\n` before sending `PING\n`; in `server.mjs`, the server sends
`HELLO\n` when its upstream connection is established, then answers `PING\n`
with `PONG\n`. Under the supplied adapter contract, `first_client_data` cannot
open the upstream until the client sends bytes. The client therefore waits for
the server while the proxy waits for the client. TCP acceptance proves only
that the local listener is reachable. Increasing the inspection timeout to ten
seconds would prolong this circular wait, not repair the handshake.

The fixed route is available at downstream acceptance without inspecting
payloads. Immediate connection allows the real server greeting to cross the
proxy unchanged. No synthetic greeting, protocol alteration, TLS/authentication
change or retry is needed.

The local contract is an explicit loopback raw-TCP endpoint, followed by a
raw-TCP connection to the adapter's trusted fixed service. The fixture supplies
no concrete upstream address beyond that route identifier. This is neither an
HTTP reverse-proxy URL nor a forward-proxy/CONNECT contract; HTTP authority and
TLS SNI are not demonstrated by these source files. Do not derive destinations
from client bytes or infer authentication from loopback access.

The application owns the handshake and operation; the adapter owns listener,
fixed destination selection, connection timing and inspection bounds. The
supplied client sends at most one `PING`; each local check opens one client
connection and permits at most one upstream attempt, with no retries. The client has no
end-to-end deadline, and the inspection timeout is not such a deadline. A real
integration still needs a caller budget and bounded upstream-connect/failure
behavior; the local check's 2500 ms deadline is a test guard, not a new policy.

Run `node verify-handshake.mjs` before accepting this proposal. It imports the
unchanged client/server fixtures and models the two adapter connection modes
using Node TCP sockets on ephemeral loopback ports. It must observe a stalled
server-first/deferred case with no upstream connection, a completed
server-first/immediate `HELLO` → `PING` → `PONG` exchange, and successful
client-first controls under both modes. It records connection creation and
bytes, checks that the policy differs only in `connect_start`, and closes every
socket and listener. See `REVIEW.md` and `handshake-check.log` for actual results.

This local model can establish the fixture's ordering consequence, not real
proxy compatibility or deployment readiness. No adapter executable, image,
version, reload mechanism or production trace was supplied. Validate the same
matrix against the chosen implementation before deployment. Test bounded
failure for an unavailable proxy, absent route or unavailable upstream without
an alternate destination or authentication/TLS bypass. Those fault cases were
not supplied as observed production behavior.

Apply connection-timing changes to new connections through the implementation's
verified update mechanism. Do not claim an existing stalled connection will
recover, an established session will migrate, or a restart is unnecessary.
Keep active sessions until completion unless an explicit recovery contract
permits interruption. Retain the previous policy for controlled rollback, but
recognize that reverting to `first_client_data` recreates this server-first
failure; it is not a functional fallback. Update, drain and rollback behavior
remain unverified in a real adapter.
