# Existing recovery contract

Publisher.create persists a business order and one outbox row in the same business transaction. The event_id is immutable and unique for this receiver; payload is the original immutable fact. Existing pending rows retain these two fields. Dispatcher.replayOne processes at most one pending row per call using the operated, single-worker replay path. Keep the existing store and public methods; do not add a broker, executor, Modulith, distributed transaction or endpoint.

The receiver has an independent commit boundary and an existing idempotency contract: repeated accept calls with the same token and same payload have one effect; the same token with a different payload is rejected. Acknowledgment can precede a local failure before outbox progress commits. The acceptance token must remain stable for that business event across retries and application recreation. Completion belongs to the outbox row, not to rerunning Publisher.create. Receiver rejection or a failure in Checkpoint.afterAccepted must propagate and leave pending work available for retry. Do not acknowledge work that did not complete. Preserve Checkpoint's call after receiver acknowledgment and before progress recording; it represents a real local operation that may fail.

Sequential retries and a single replay worker are in scope. Existing ordinary database durability is assumed; this local fixture does not test physical crash guarantees or concurrent workers. ReceiverClient in support is a frozen deterministic surrogate for the described provider contract, not production HTTP code. Its count is observation only. lib, support and all contracts are read-only.
