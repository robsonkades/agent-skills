The implementation required a correction. BEFORE_COMMIT executed the receipt while
the booking was still uncommitted, and a rejected receipt body rolled back the
mandatory booking/stock transaction. The original smoke test passed because it only
covered a valid body after completion.

The repair changes two transaction annotations: BookingListener handles AFTER_COMMIT,
and the separately injected ReceiptWriter bean uses REQUIRES_NEW on businessTx.
The proxy creates a real receipt transaction around both inserts, so a rejected body
also removes its header. BookingService remains REQUIRED; the public operation,
event identity, schema, stock rule and observer position are unchanged.

AFTER_COMMIT transactional events run through afterCompletion in this Spring version.
Its existing failure handling logs callback errors without propagating them to the
completed business call. No additional catch is necessary. Resources may still be
bound during completion, so the writer needs an explicit new transaction. These
details were checked against [TransactionPhase 7.0.9](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/transaction/event/TransactionPhase.html),
[TransactionSynchronization 7.0.9](https://docs.spring.io/spring-framework/docs/7.0.9/javadoc-api/org/springframework/transaction/support/TransactionSynchronization.html)
and the tagged [callback implementation](https://raw.githubusercontent.com/spring-projects/spring-framework/v7.0.9/spring-tx/src/main/java/org/springframework/transaction/support/TransactionSynchronizationUtils.java).

Actual observations, using Spring beans and fresh independent READ_COMMITTED
connections after completion:

| Scenario | Booking / header / detail | Available stock | Business result |
| --- | --- | --- | --- |
| Valid 12-character receipt | 1 / 1 / 1 | 19 | Success |
| Invalid 13-character receipt | 1 / 0 / 0 | 19 | Success |
| Unavailable stock | 0 / 0 / 0 | 0 | Failure |
| Nontransactional event | 0 / 0 / 0 | 20 | No receipt |
| Enclosing owner commits | 1 / 1 / 1 | 19 | Success |
| Enclosing owner rolls back | 0 / 0 / 0 | 20 | Failure |
| Later beforeCommit callback rejects | 0 / 0 / 0 | 20 | Failure |

The diagnostic observer saw the booking on an independent READ_COMMITTED connection
before each actual receipt write, with no header yet. Work remained synchronous.
No observer ran for rollback or nontransactional publication. Before an enclosing
owner completed, neither mandatory state nor receipt was externally visible.

Regression was first run against the original implementation: four scenarios failed,
including booking visibility and invalid-body policy. A second control added only
REQUIRES_NEW while retaining BEFORE_COMMIT: four scenarios still failed, and the late
rollback left header/detail rows despite zero bookings. This directly rejects the
teammate's blanket fix. Both failing runs remain in checks/*.json.

Final checks: `node check.mjs` passed, and `node check.mjs work.Regression` passed all
seven scenarios. The invalid-body run emitted Spring's expected SEVERE callback log;
its command returned normally and the header was rolled back. Logs preserve stdout,
stderr, exit codes and times. RUNBOOK.md describes the selected behavior.

These results establish local JDBC/H2 behavior for Java 25 and Spring 7.0.9. They do
not establish crash durability, production-database guarantees, distributed
deduplication or JPA behavior. Receipt loss on failure/interruption remains accepted.
No recovery store, dependency, executor or external service was added. Reads and
writes followed the task's procedural boundaries; no OS isolation is claimed.
