The operator calls Dispatcher.replayOne until it returns false, under the existing one-worker policy. Pending rows are outbox.done=false. Retry the retained work after resolving a receiver or checkpoint error; never resubmit a committed order merely to redeliver.

The persisted event_id is the receiver acceptance token. Preserve it and the original payload for every retry, including after application recreation. A receiver acknowledgment can survive a failed Checkpoint.afterAccepted while the outbox row stays pending. A retry repeats acceptance with the same token/payload, then retries the checkpoint before recording done=true. Receiver rejection and checkpoint failure propagate; they do not complete the outbox row. Checkpoint itself may run again and must support the operational retry policy.

Regression commands, run from this directory in this order:

```text
node check.mjs
node check.mjs work.RecoveryRegression failure
node check.mjs work.RecoveryRegression replay
node check.mjs work.RecoveryRegression controls
```

The failure phase initializes disposable file databases under .build/recovery-business and .build/recovery-receiver, commits an order, then fails after receiver acknowledgment. The replay phase runs in a fresh JVM and uses the retained files without recreating the order or schema. Run failure before each replay to establish its starting state. These phases prove recovery after orderly process exit with H2 files and the contracted local receiver surrogate. They do not establish physical crash durability, network-provider behavior, concurrent-worker safety, or exactly-once checkpoint execution.

Previously accepted deliveries made with random tokens cannot be deduplicated retroactively by deriving event_id: the old random token was not persisted. Reconcile that pre-fix failure window with the receiver before retrying affected legacy work. The stable-token guarantee applies when acceptance starts with the corrected path.
