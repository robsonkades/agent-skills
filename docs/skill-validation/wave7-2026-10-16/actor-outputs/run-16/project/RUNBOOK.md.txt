The operator calls Dispatcher.replayOne until it returns false, under the existing one-worker policy. Pending rows are outbox.done=false. Retry the retained work after resolving a receiver or checkpoint error; never resubmit a committed order merely to redeliver.

The outbox event_id is the receiver acceptance token. Keep it and the original payload unchanged across retries and application recreation. The receiver commits independently and may acknowledge before Checkpoint.afterAccepted fails. Such a failure propagates, leaves done=false, and may leave an accepted receiver effect. Replay calls the receiver with the same identity and payload, then calls the checkpoint again, and only then commits done=true. A rejection must be investigated without changing the token to bypass receiver identity checks.

Inspect retained work with `select event_id,payload from outbox where done=false order by event_id`. After resolving the error, invoke the existing Dispatcher.replayOne entrypoint one call at a time. Each successful true result completes at most one row; false means no pending row was selected. Recheck pending work after errors. Do not run competing workers under this contract.

Run `node check.mjs work.Regression` for checkpoint failure/replay, context recreation, receiver rejection, identity conflicts, original payload preservation, publisher rollback, and one-row processing. Run `node ../checks/restart.mjs` for a separate-JVM recovery check using disposable file-backed H2 databases under .build: the first process exits after an acknowledged effect and failed checkpoint; the second replays the retained row. This demonstrates orderly process recreation with retained local data and the frozen receiver surrogate. It does not test forced process kills, power loss, physical storage durability, concurrent workers, or a production provider. Ordinary database durability and the stated receiver identity contract remain assumptions.
