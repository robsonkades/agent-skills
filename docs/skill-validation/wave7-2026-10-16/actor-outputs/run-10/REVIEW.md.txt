# Mandatory receipt review

Decision: **unchanged application implementation**. The supplied implementation
already satisfies the accepted local transaction contract. Added a regression,
a reproducible negative control, and operating notes; preserved all application
source files byte for byte.

`BookingService.place` is a Spring-managed REQUIRED operation using `businessTx`.
It inserts the booking, publishes the event, and reserves stock. The existing
BEFORE_COMMIT listener calls the writer while that transaction is still active.
Both receipt statements use its bound JDBC connection. Receipt rejection therefore
aborts completion and rolls back the earlier header, booking, and reservation.
Without an active transaction the listener does not execute. When an outer caller
owns the transaction, returning from `place` does not commit that caller's unit.
These semantics agree with the official Spring documentation for
[transaction-bound events](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)
and [transaction propagation](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/tx-propagation.html).

The reported missing receipt did not establish a defect in this mandatory-receipt
contract. Rejection and owner rollback require the receipt to be absent.
REQUIRES_NEW would give the writer an independent transaction, losing visibility
of the pending publisher state and allowing durability independent of its booking.
The proposed blanket change is therefore incompatible with this contract.

The new regression calls actual Spring beans against the supplied local H2
database. All final-state assertions run after transaction completion:

| Observation | booking/header/body | available stock |
| --- | --- | --- |
| Successful 12-character body | 1/1/1 | 19 |
| 13-character body, DataIntegrityViolationException | 0/0/0 | 20 |
| Unavailable stock, IllegalStateException | 0/0/0 | ready 20; sold-out 0 |
| Publication without transaction | 0/0/0 | 20 |
| Existing caller commits | 1/1/1 | 19 |
| Caller throws after `place` returns | 0/0/0 | 20 |
| Caller throws after header and body were written | 0/0/0 | 20 |
| Caller marks rollback-only | 0/0/0 | 20 |

Inside the actual writer, the diagnostic observer sees booking=1 and stock=19,
with no receipt writes yet. A separate connection sees booking=0 and stock=20.
The late-failure scenario additionally verifies both receipt rows exist inside
the owner's transaction before deliberately aborting it, while separate reads
still see no receipt. This checks owner control beyond an early service failure.

`node check.mjs` and `node check.mjs work.ReceiptContractRegression` passed.
`node ../checks/requires-new-control.mjs` compiled a replacement writer solely
under `output/checks`. The same regression rejected it with
`writer sees uncommitted publisher booking: expected=1, actual=0`; its Java exit
was 1, as expected, and the control runner passed. Production sources were never
mutated for this experiment.

Two preliminary path mistakes are retained in the execution record: reading
README/REQUEST/CONTRACT at the actor root and invoking `check.mjs` there. They were
corrected to the authorized project paths. Version-specific documentation URLs
were unavailable; the official current documentation identified Spring 7.0.9.

The tests establish observed local JDBC/H2 behavior, not production database
crash durability, concurrent workload behavior, distributed deduplication,
delivery guarantees, or JPA semantics. No application service was connected to
an external provider, no dependencies were installed, and no agent configuration
was modified.
