Call BookingService through the configured Spring application context. The schema is initialized by the existing launcher/tests. Inspect booking, receipt and stock state outside the completed command. Document the selected failure behavior here if it changes.

The existing mandatory-receipt behavior is retained. `place` uses REQUIRED with
`businessTx`; the BEFORE_COMMIT listener and both writer statements use that same
transaction. A body longer than 12 characters fails completion and rolls back the
booking, header, body, and stock reservation. A caller with an existing transaction
owns completion; a successful nested call does not establish durability. Publication
without a transaction does not invoke the listener.

Run `node check.mjs` and `node check.mjs work.ReceiptContractRegression` from this
directory. The regression uses real Spring beans and reads state after completion.
It covers 12-character success, oversized-body rejection, unavailable stock,
nontransactional publication, successful caller-owned completion, caller failure
both before and after receipt writes, and rollback-only completion. Its diagnostic
observer verifies visibility of the pending booking/reservation and invisibility
from a separate connection before the receipt header is written.

After compiling the regression, `node ../checks/requires-new-control.mjs` compiles
an isolated replacement writer under `../checks` and verifies that the regression
rejects the proposed REQUIRES_NEW change. It does not edit application sources.

These disposable H2 checks do not establish crash durability, behavior on another
database, distributed delivery/deduplication, or JPA transaction semantics.
