Call OrderService and MetricsService through their configured Spring beans. Inspect the corresponding datasource after the call completes.

`OrderService.place` explicitly selects `ordersTx`, which manages the same
`ordersDataSource` used by `ordersJdbc`. Order insertion, stock reservation and the
local notifier rejection therefore share one transaction. `metricsTx` remains
primary, and unqualified `MetricsService.sample` continues to use it.

The original failure was manager selection, not self-invocation or a missing
rollback rule. The original Spring bean invocation started a metrics transaction:
the notifier observed `active=true`, `ordersAutoCommit=true` and
`metricsAutoCommit=false`. The active probe alone cannot prove that the orders
connection participates. Runtime exceptions already trigger Spring's default
rollback policy; the collaborator interface declares no checked exceptions.

Run from this project directory:

```text
node check.mjs
node check.mjs work.Regression
```

The regression uses actual configured Spring beans and a primary test notifier
that can reject after both writes. It checks committed state after calls return
or throw, with no enclosing test transaction: success, unavailable stock, notifier
rejection with preserved exception/cause, duplicate insertion, metrics commit and
metrics rollback without changes to committed orders. Resource diagnostics are
supporting evidence, not a substitute for persisted-state assertions.

These checks use disposable local H2 databases. They do not establish production
database crash recovery, external notification delivery, distributed atomicity or
JPA behavior.
