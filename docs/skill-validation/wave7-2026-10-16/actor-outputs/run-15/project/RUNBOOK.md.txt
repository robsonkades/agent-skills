The operator calls Dispatcher.replayOne until it returns false, under the existing one-worker policy. Pending rows are outbox.done=false. Retry the retained work after resolving a receiver or checkpoint error; never resubmit a committed order merely to redeliver.

The acceptance token is the retained row's immutable event_id. Replay always sends that token with the original payload. Receiver acknowledgment commits independently; if Checkpoint.afterAccepted fails, the local transaction rolls back and the row stays pending. A later replay sends the same identity, so the contracted receiver returns the existing acceptance without another effect. The checkpoint still runs before done is committed. Receiver rejection, including identity reuse with a different payload, propagates and leaves the row pending; investigate the rejection without changing the event's identity or original fact.

Run `node check.mjs` for normal delivery and `node check.mjs work.RecoveryRegression` for recovery and transaction regressions. The latter creates disposable file databases under `.build`, runs the acknowledged-but-checkpoint-failed phase in one JVM, then reopens the retained databases and completes replay in a separate JVM without calling Publisher.create again. It also checks publisher rollback when outbox insertion fails, receiver rejection, payload conflict, distinct events with equal payloads, and one-row replay.

This demonstrates recovery after application/JVM recreation using retained local database state and the supplied idempotent receiver contract. The JVMs exit normally after the injected failure. It does not simulate abrupt process termination, power loss, production storage durability, a real provider, concurrent replay workers, or a globally atomic transaction across receiver and business database. Normal database durability and one replay worker remain required.
