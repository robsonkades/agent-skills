Approve the exact proposal semantically; keep `solution.sql` unchanged. Performance approval is unsupported by the supplied evidence.

The schema declares `active boolean NOT NULL CHECK(active IN (false,true))`. Let `p` be `active = true` and `q` be `amount >= 100`. For each permitted invoice:

| active | Original predicate | First branch | Second branch |
| --- | --- | --- | --- |
| true | true | emits once | excludes |
| false | q | excludes | emits exactly when q is true |

Thus the branches partition the original qualifying invoices. An invoice matching both predicates appears once; different invoices with equal `customer_label` remain separate rows because the operator is `UNION ALL`. Both branches retain `tenant_id = :tenant`, the same projection, and the final ascending `ORDER BY customer_label` applies to the combined output. This reasoning covers every permitted row, not merely the fixture.

`NOT (active = true)` is safe here because `active` cannot be null. Under a nullable schema it could lose invoices where `active` is null and the amount qualifies, but that is not this contract and does not justify changing this correct proposal. PostgreSQL documents the relevant [three-valued logic](https://www.postgresql.org/docs/17/functions-logical.html) and [UNION ALL duplicate preservation](https://www.postgresql.org/docs/17/queries-union.html).
