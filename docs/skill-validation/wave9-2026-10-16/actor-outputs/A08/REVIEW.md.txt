# RetryPlan repair

`RetryPlan.next` now implements the checked-in fixed scheduling policy while preserving its public signature and `Plan` record. Only `RetryPlan.java` was changed among the supplied project files.

The previous implementation allowed another call when `completed == maxAttempts`, used the wrong exponential index, selected the smaller delay instead of honoring both delays, and allocated attempt time without deducting the wait and reserve. Its admission sum could overflow, and Java's shift masking/overflow broke large retry counts and bounds.

The repair first stops when the call count is exhausted. It computes elapsed time as `now - start`, which remains correct across signed `nanoTime` wrap under the contract's elapsed interval `[0, 2^63)`. Expired budgets are rejected. It compares the reserve with the remaining budget before subtraction and checks that `minimumWork` fits. No positive-input limit was narrowed.

For retries, the exponent is `completed - 1`. If it is at least 63, every positive base times that power exceeds every valid delay cap, so the window is the cap. Otherwise, comparing `base` with `delayCap >> exponent` determines whether the mathematical product exceeds the cap before any left shift. A performed shift therefore fits in a positive `long` and equals the required window.

The wait is exactly `max(draw(window), serverMinimum)`. Advice that cannot fit is rejected, never shortened. Comparing wait with `available - minimumWork` avoids an overflowing sum. Accepted attempt time is exactly `min(attemptCap, available - wait)`, with the reserve already removed. Equality admits an exact fit. Rejections always return both durations zero. Initial calls ignore server advice and neither wait nor draw. Known-impossible cases can reject before drawing.

Validation used the actual output implementation through the supplied runner. `node run.mjs Verification` compiled with `javac --release 17` and passed 182,506 deterministic calls. The verification compares exact plans with an independent `BigInteger` budget model and mathematical jitter windows, checks draw bounds/counts, and checks admitted budget invariants. Cases cover initial calls, both maximum-wait operands, exact and one-unit-short fits, clipping to the attempt cap, exhausted attempts, expiry, signed clock wrap, near-`Long.MAX_VALUE` values, exponential overflow, and retry counts beyond Java's masked shift range. Draws use zero, midpoint, and the largest allowed value; no real randomness is used. `node run.mjs Smoke` also passed. The installed runtime/compiler reported Temurin/OpenJDK 25.0.3. Every Java subprocess was bounded by 20 seconds. SHA-256 comparisons confirmed the five immutable output copies match their input originals.

This is arithmetic evidence for the supplied contract, not a latency or provider guarantee. The helper neither sleeps nor cancels work, enforces no actual execution timeout, and does not classify an operation as safe to retry. A caller must remeasure and recheck admission after real waiting or intervening work, account for all relevant attempts, propagate the remaining budget, and own cancellation. Timeout after dispatch can leave an external effect unknown; safe repetition requires the operation's actual idempotency/recovery contract. No provider, database, SDK, durable operation identity or retention contract is supplied here. Those guarantees, server work release, and fleet behavior remain unverified.

Only the supplied idempotency and timeouts-and-deadlines skills and the local deadline-propagation reference were used. Routes to other skills were outside the permitted context and were not opened. No network, service, global configuration, dependencies, installation or delegation was involved.
