# RetryPlan repair

The implementation now follows the checked-in fixed scheduling policy while preserving the public method and Plan record. Only RetryPlan.java was changed among the supplied files.

The original implementation used the wrong retry exponent, selected the smaller of local jitter and server advice, admitted one call beyond maxAttempts, and allocated attempt time without subtracting the wait and reserve. Adding wait + minimumWork + reserve could also overflow, and Java's masked shift distance allowed large retry ordinals to restart the backoff.

The corrected arithmetic is:

- Stop when completed >= maxAttempts, including the first call in the total limit.
- Compute elapsed = now - start. Under the supplied true-elapsed horizon below 2^63 nanoseconds, this subtraction handles negative readings and signed wrap. Reject expiry before subtracting elapsed from total.
- Compare reserve against remaining before subtracting it. Require minimumWork to fit before computing maximumWait = remaining - reserve - minimumWork. These guarded subtractions avoid overflowing sums.
- On the initial call, wait is exactly zero, server advice is ignored, and draw is never called.
- On retry, exponent is completed - 1. Saturate base * 2^exponent before applying delayCap; guard exponents >= 63 before Java can mask the shift distance. Draw once from the resulting positive half-open window.
- Choose wait exactly max(localDraw, serverMinimum). Reject advice or a drawn wait that cannot fit; never reduce either to force admission.
- Allocate attemptNanos exactly min(attemptCap, remaining - reserve - wait). The strict rejection comparisons admit exact fit. Every rejection returns zero durations.

No narrower duration, clock-origin or attempt-count limits were introduced.

Validation used the actual deliverable with javac --release 17 on the observed Temurin JDK 25.0.3. Before the repair, node run.mjs Verification failed on the first regression: an initial call with total 100 and reserve 25 allocated 100 instead of 75. After the repair, the same command passed 88,830 plans and 2,878 retry draws. Verification.java checks 30 explicit cases, 76,800 combinations in a small input domain and 12,000 deterministic seeded cases against a BigInteger model. It compares exact Plan values and supplied draw bounds, including cap saturation, huge counts, negative/wrapped clocks, large durations, initial-call behavior, server minima and exact-fit rejection boundaries. node run.mjs Smoke also passed. SHA-256 comparisons confirmed all five immutable supplied output files still match input/project. Every Java subprocess used a 20-second limit.

This is a planning helper, not a retry executor. The caller must recheck elapsed budget after actual waiting, configure attempt/body timeouts, honor cancellation, and account for unfinished earlier work. The helper cannot establish whether a failed attempt applied, authorize replay of ambiguous effects, persist idempotency state, validate provider replay guarantees, coordinate retries across layers, or bound fleet load. No provider, database, network, wall-clock latency, cancellation release or distribution behavior was exercised. A deterministic local check establishes the tested scheduling arithmetic, not production effects or timing.

Only the supplied skill snapshots and their relevant retry/deadline references were used. Their routes to other packages were not followed; those broader concerns remain outside this local exercise.
