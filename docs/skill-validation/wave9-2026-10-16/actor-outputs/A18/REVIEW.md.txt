# RetryEngine repair

The repaired runner retains the original public signature and compiles against Java 17. The supplied runner used Temurin JDK 25.0.3 with `javac --release 17`; Node was v25.6.1.

The original implementation changed the intent ID for each call, ignored terminal store snapshots, treated uncertain outcomes as rejection, used the smaller delay, and retained responses during sleep. It also lacked deadline, cancellation and interruption admission checks. The new regression failed against that original implementation with `AssertionError: intent identity or payload changed` while exercising a terminal snapshot.

The implementation now returns existing APPLIED/REJECTED snapshots unchanged with zero calls. Each dispatched attempt receives the supplied immutable intent and configured attempt timeout. Only authoritative OK produces APPLIED and its actual receipt. Initial or newly observed UNKNOWN survives later transient/permanent outcomes, exhausted attempts, denied tokens, insufficient time and cancellation. Interruption from `operation.call` persists UNKNOWN and propagates. Other interruptions propagate without resetting previously persisted uncertainty.

Every returned reply is closed exactly once through try-with-resources before retry admission, sleep, another call or normal return. Retry delay is `max(localWaitNanos, serverMinimumNanos)`, including an UNKNOWN reply's minimum. Admission checks the full attempt and reserve; retry admission additionally checks the entire wait and acquires one token. Subtraction after comparison avoids overflow, including values near `Long.MAX_VALUE`. The loop refreshes budget, cancellation and interruption after sleep, so an oversleep may consume a token without authorizing a call. No new jitter or unconditional refusal policy was introduced.

Validation executed:

- `node run.mjs Verification` against the original: failed as described above.
- `node run.mjs Verification` after repair: 27 scenarios passed. Repeated after strengthening assertions that UNKNOWN is persisted before retry admission, sleep and another call: all 27 passed.
- `node run.mjs Smoke`: passed.
- Byte comparison against input verified all seven immutable output copies unchanged. Final implementation and regression hashes are recorded in `execution.json`.

The scenarios cover completed snapshots, receipt replay, stable identity/payload, retry success, both delay sources, initial and subsequent uncertainty, permanent rejection after uncertainty, exhaustion, admission refusal, exact budget fit, arithmetic overflow, token denial, oversleep, cancellation before/after sleep, pre-interruption, dispatch interruption and sleep interruption. Assertions exercise actual `RetryEngine.execute`, including response closure and persisted outcomes.

These are authored component simulations. `Ports.Store` durability/atomicity and `Contract.REPLAY_SAFE=true` are supplied premises; no database, isolation level, HTTP endpoint, provider API version, tenant namespace or retention horizon is supplied or validated. The code guards the false replay-safety branch, but the immutable compile-time constant is true, so that branch was not executed. No reconciliation operation exists here: unresolved outcomes remain UNKNOWN. Integration must establish same-intent receipt recovery and replay scope/retention, map transport outcomes correctly, enforce the actual timeout and measure cancellation/resource release. The tests do not establish production deduplication, crash recovery, wall-clock limits, physical cancellation or fleet behavior. Broader skill routes such as consistency-models and distributed-transactions-and-sagas were outside the supplied context and were not opened.

Only the authorized implementation and task artifacts under this output directory were changed. No repository-wide verification applies to this isolated Java exercise; the provided runner was used. No network, installation, real agent configuration, delegation or background process was involved.
