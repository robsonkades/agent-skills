# Account concurrency test review

The existing stress oracle has a coverage gap: an account that always refuses leaves
`succeeded = 0`, `refused = 32_000`, and `balance = 10_000`, satisfying all its assertions.
`docs/account-contract.md` requires acceptance for a positive, affordable withdrawal when
the gate is free. Added `affordableWithdrawalsAreAcceptedWhenTheGateIsFree` to
`test/AccountTest.java`: a fresh account must accept 30 from 100, retain 70, then accept
the remaining 70 and retain zero. There are no competing workers in this test, so its
acceptance oracle does not depend on scheduling. Its timeout is five seconds.

Preserved the original stress test and its continuing contract purpose: 20 repetitions,
32 virtual workers, 1,000 attempts per worker, bounded start barrier, retained Futures,
grouped worker failures, success/refusal accounting, nonnegative final balance and
quiescent conservation. Its 20-second shared Future deadline, unconditional cancellation
and shutdown, separate two-second termination assertion, and 30-second test timeout are
unchanged. Production code, Java target 21, no-preview configuration, and dependency
versions are unchanged.

## Limits

A green run shows no checked invariant failed in these sampled executions; it does
not prove thread safety, full history linearizability, or correctness on other
hardware/JDKs. Compilation targeted 21, but runtime execution was on 25.0.3.
No mutation experiment or additional scheduler/platform matrix was run. The
always-refuse coverage gap above follows from the assertions, not an executed mutant.
The busy-gate refusal schedule was not forced through `holdGate`; the contract
allows refusal while busy and does not require a fixed rejection count or fairness.
No such stronger oracle was introduced. Cancellation/interruption in this fixture
remain harness cleanup, not newly invented account API promises. Timeouts are test
budgets and do not establish production latency guarantees.
