# Client rollout compatibility review

The candidate cannot roll out against the authoritative stored state while preserving placement and avoiding migration. `rollout.md` now rejects the draft recommendation. No deployment was performed.

## Routing and contract inspected

The deployed selection under review is `candidate.properties`. `ClientRouter` reads `keyPrefix` (default empty), then passes `prefix + requestKey` to both `HashRing.owner` and `HashRing.owners(..., 3)`. The accepted file contains `keyPrefix=`; the candidate contains `keyPrefix=cache:`. These are the only properties in the supplied files. For `user:2`, the accepted hash input is `user:2`; the candidate input is `cache:user:2`. The inspected routing path does no normalization or additional field framing.

The retained placement contract is epoch E, four physical IDs n1..n4 with weights 1, V=1024 per weight, and three clockwise, ordered, distinct physical owners. Each virtual-point token is exactly `node + '#' + i`, for i=0..1023. Keys and tokens use UTF-8. The hash is the pinned Guava 33.5.0-jre `Hashing.murmur3_128()`: MurmurHash3 x64 128, seed zero. See the [versioned Hashing API](https://guava.dev/releases/33.5.0-jre/api/docs/com/google/common/hash/Hashing.html#murmur3_128()). Positions use the first eight hash bytes as a little-endian long via `asLong()`, per the [versioned HashCode source](https://raw.githubusercontent.com/google/guava/v33.5.0/guava/src/com/google/common/hash/HashCode.java). Ring ordering is unsigned; equal hashes use token lexicographic order. Primary lookup uses ceiling then wraps to the first point; replicas walk the ring and skip repeated physical IDs.

Epoch E is supplied fixture metadata; the inspected classes do not enforce epochs. The supplied skill documents pinned Guava malformed-UTF-16 replacement behavior, but this fixture does not verify malformed or normalization-sensitive inputs. This review does not introduce a new input policy.

`check.mjs` explicitly compiles with `--release 16`, without preview, and resolves only the declared Guava JAR. The declared compiler and runtime both report Temurin 25.0.3. No Java baseline, dependency, production class, configuration, data model, topology or frozen vector was changed.

## Limits and decision conditions

The supplied frozen fixture contains one ASCII key, primary and ordered replicas, with provenance naming the accepted unmodified Java ring and Guava 33.5.0-jre. It has no frozen key-byte/hash values or independent node-point vectors. Its cited retained control output was not supplied or searched for. This focused check does not establish agreement for all strings, ports or environments, nor exercise deliberate collisions, wrap-around, malformed input, failure domains or migration behavior. No production workload, byte/request distribution or transfer budget was supplied. Additional measurements cannot make the demonstrated mismatch compatible, so no tuning or broad simulation was justified.

Compilation used the Java 16 release API target on JDK 25.0.3; this is not an execution test on a Java 16 runtime or the production image. No production access, deployment, dependency installation, catalog regeneration or repository-wide `npm run verify` occurred: this standalone task's documented runner is `node check.mjs` and work was confined to the assigned directory.

The current gate deliberately remains red for the unchanged incompatible candidate. To reconsider a no-migration rollout, select empty-prefix/raw-key routing in the actual candidate and rerun the gate, retaining the rest of the contract. A deliberate prefix change would instead need an explicit epoch and verified authoritative-data handoff, as described in `rollout.md`; this task does not authorize that alternative.
