## Limits and decision boundary

The existing join sample moved 20.94% of 10,000 synthetic keys to n5, inside its
fixed 18%-22% tolerance. That is neither a production workload/balance measurement
nor evidence that an authoritative-state handoff is safe. The new frozen fixture
contains only one ASCII key and primary/replica expectations; it contains no
frozen encoded bytes, hash, Unicode/malformed-input cases, or deterministic
collision/wrap-around vectors. No broader coverage is claimed or fabricated.
There is no new normalization, framing or malformed-input validation in the
inspected router/ring; their existing behavior is retained. No throughput,
bytes/QPS skew, failure-domain guarantees or exhaustive cross-language agreement
were tested. Execution used Java 25, not a Java 16 runtime; `--release 16`
compilation did succeed. The fixture has no deployment image to inspect.

These limits do not overturn the decision for identical supplied routing and
configuration. An observed mismatch or a changed placement parameter would
change it. Authoritative state must not simply refill after a remap: a future
ownership change needs a separate coordinated epoch/handoff decision, as described
in `rollout.md`. No algorithm/V tuning or migration was introduced.

The authorized task check is `node check.mjs`, which ran successfully. Repository
`npm run verify` was not run: this is an isolated Java fixture, and the task
forbids work outside it. No dependencies were installed, no production contact or
deployment occurred, and no real agent configuration was altered.
