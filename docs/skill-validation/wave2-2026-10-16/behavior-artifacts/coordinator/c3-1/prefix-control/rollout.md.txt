# Rollout recommendation

Reject the current candidate for rollout against authoritative stored state without migration. The existing recommendation is revised because the configured client changes placement.

Epoch E fixes Murmur3-128, UTF-8 encoding of the raw request key, V=1024, four equal-weight nodes n1..n4, and three ordered distinct replicas. `ClientRouter` prepends `keyPrefix` before both primary and replica lookup. `accepted.properties` has an empty prefix; `candidate.properties` specifies `cache:`. Consequently, the candidate hashes `cache:user:2` for the request key `user:2`.

The frozen `accepted-vectors.json` and the focused check through both `ClientRouter.owner` and `ClientRouter.owners` show:

| Configuration | Primary | Ordered replicas | Compatible |
| --- | --- | --- | --- |
| Accepted, empty prefix | n2 | [n2, n3, n4] | Yes, matches the frozen vector |
| Candidate, `cache:` prefix | n1 | [n1, n3, n2] | No |

`node check.mjs` compiles successfully with `--release 16`, passes the existing ring-point and join checks (2,075 of 10,000 keys moved to n5), validates the accepted control, then exits 1 on candidate incompatibility. See `logs/compatibility-check.log`.

Identical vnode positions and monotonic node addition do not verify identical request-key serialization. The join test uses the candidate prefix on both sides, so it cannot detect this placement-contract change. The failed primary and ordered-replica comparison is sufficient to block this candidate; the movement count does not measure authoritative-to-candidate drift.

A compatible revision must preserve raw-key routing, for example by restoring an empty `keyPrefix`, and rerun this compatibility gate before reconsidering rollout. No algorithm, V, weights, Java baseline, data model, configuration, or production state was changed in this review. No deployment was performed. One frozen vector disproves compatibility; it does not quantify all affected keys or demonstrate data migration, failover, or storage behavior.
