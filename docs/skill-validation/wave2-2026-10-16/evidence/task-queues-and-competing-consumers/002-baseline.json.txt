If the message is not deleted before expiry — crash, GC pause,\nslow dependency — it becomes eligible for another receive. A later receiver may overlap the\noriginal handler or may arrive after it finishes. This recovery mechanism permits duplicate\nexecution; expiry alone neither proves a second execution nor stops the first.\n\nNames and semantics differ. SQS has per-receipt visibility and can duplicate even within that\nperiod; RabbitMQ AMQP 0-9-1 manual acknowledgements belong to the delivery's channel, with\nunacknowledged work requeued on channel/connection closure; JMS CLIENT_ACKNOWLEDGE acknowledges\nall messages delivered by that session, not just the referenced message; database\nqueues implement whatever claim transaction/clock/fencing was designed. Verify the broker's\nredelivery, ordering, acknowledgement scope and stale-handle behavior rather than translating all\nof them into one lease model.\n\n## The duplicate-work window\n\n```\nt0   W1 receives msg, lease expires at t0+30s\nt0   W1 begins handler (this one will take 45s: dependency is slow today)\nt30  lease expires; broker makes msg visible again — no error is raised anywhere\nt31  W2 receives the same msg, begins the same handler\nt45  W1 finishes, applies the side effect, calls delete with its older receipt\nt76  W2 finishes, applies the side effect a second time\n```\n\nBetween `t31` and `t45` two workers hold the same item with **no mutual exclusion between\nthem** in this example. No application retry or exception is required. Correlate task IDs,\nattempt intervals and effect records with available redelivery metadata; a counter is neither\nthe only observable evidence nor universally available. SQS DeleteMessage can return success\nfor an old receipt handle without deleting the message. An API success does not prove that\nredelivery was prevented, and deletion does not cancel an already-running handler.\n\n## Choosing the timeout\n\nLet `E` be exposure from receive until successful acknowledgement:\n\n```\nE = receive-to-start + handler elapsed time (including downstream waits) + acknowledgement\nvisibility timeout > selected tail(E) + clock/client/broker-resolution margin\n```\n\n- **Select the tail from an objective.** A higher timeout reduces expiry overlap but delays\n  crash recovery; a lower one recovers sooner but increases duplicate concurrency. p99.9 is an\n  example only when its nominal 0.1% premature-expiry rate is affordable and the measured sample\n  covers overload, pauses and dependency degradation. Timeouts censor the observed tail.\n- **Prefetch creates waves.** All `B` leases begin at receive. Other bounded intake mechanisms can be valid; choose\nacknowledgement placement from the required loss/duplicate policy (`delivery-semantics`).\n\nPseudocode for a pull consumer; receive/renew/ack operations are broker-specific:\n\n```text\npoller owns each permit until a handler explicitly accepts it\nwhile intake is open:\n  acquire one permit interruptibly\n  try bounded receive of at most one delivery\n  if receive fails or returns empty: release permit in finally; classify/back off; continue\n  unknown receive outcome may leave a broker-side delivery hidden until recovery\n  under lifecycle gate shared with shutdown:\n    if intake closed: retain delivery for bounded return/recovery; release permit\n    otherwise transfer delivery + permit only after successful handler submission\n  on submission rejection: try bounded recovery; release permit exactly once in finally\n\nhandler owns accepted delivery + permit:\n  start bounded, observable lease renewal where the broker supports it\n  execute repeat-safe effect\n  record effect success, then attempt ack/delete\n  distinguish effect failure, ack failure/unknown outcome, and renewal cleanup failure\n  do not issue a second nack just because cleanup failed after confirmed ack\n  stop/join renewal and release permit in the actual handler's outer finally\n  do not release running-work capacity merely because its Future reports cancellation\n\nshutdown:\n  atomically close intake through lifecycle gate\n  cancel/wake bounded receive and wait for poller exit; resolve any fetched delivery\n  close handler submission and drain to a shared monotonic deadline\n  at deadline request cooperative cancellation and stop renewal as policy requires\n  report still-running handlers; recover unstarted deliveries through broker semantics\n  release delivery early only with old-work overlap covered by the effect contract\n```\n\nThe permit above counts local active work. An unknown receive or failed return can still leave\nbroker-side work outstanding after that permit is released. Track that uncertainty under a\nseparate finite recovery budget and pause further intake when the budget is exhausted; a\nlocal permit count alone does not bound all broker-side in-flight deliveries.\n\nReserve one permit per delivered item for batch receive. For push consumers, align broker\ncredit/prefetch with bounded dispatch instead. Serialize ack on its owning channel/session where\nthe client requires it; JMS session-wide acknowledgement is not a per-message operation.\nRabbitMQ 4.2 AMQP 0-9-1 QoS prefetch does not limit `basic.get` polling; use the limit that\nactually governs the selected delivery API. Changing prefetch with deliveries already in\nflight can temporarily exceed the new count.\n\n**Batch outcome accounting.** SQS `DeleteMessageBatch` and `ChangeMessageVisibilityBatch` can\nreturn HTTP 200 with both successful and failed entries. Correlate each response entry ID to\nthe submitted delivery/receipt attempt; do not treat the batch as one acknowledgement or one\nrenewed lease. Preserve successful entries and classify failed entries individually. Retry\neligible failures within the recovery/renewal budget; a stale receipt needs broker-specific\nrecovery, not an endless retry of that handle.\n\nFor example, if renewal succeeds for A but fails for B, only A has a confirmed new interval.\nB needs recovery under its remaining known headroom and the effect contract. A request timeout\ninstead leaves application of the extension uncertain; do not assume all entries failed or\ngive them all a new deadline. Deletion failure after a committed effect calls for settlement\nor redelivery reconciliation, not automatically rerunning the business effect.
