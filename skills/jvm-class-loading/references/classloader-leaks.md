# Classloader leaks

## Why this is invisible

Ordinary named classes are normally unloadable only when their defining loader is unreachable;
a single strong path to one child object can therefore retain the loader and its class metadata.
Weak hidden classes are an exception and may unload independently. The retaining heap object is
often tiny while much of the cost is native Metaspace, which a heap dump does not size directly.

The consequence: memory dashboards look healthy right up to
`OutOfMemoryError: Metaspace`, or to an OOMKill if `MaxMetaspaceSize` was never set.

## Confirm before hunting

```bash
jcmd <pid> VM.classloader_stats     # before N reload cycles
# ... N cycles ...
jcmd <pid> VM.classloader_stats     # after
```

Compare equivalent lifecycle cohorts only after class unloading had an opportunity to run.
Persistent obsolete loaders of the same `Type`, coupled with flat workload/cardinality, strongly
indicate retention. A monotonic counter alone can also mean legitimate new code paths, no
unloading cycle yet, a collector/configuration that does not unload classes, or strong hidden
classes generated by design.

Also expose, for continuous monitoring:

- `LoadedClassCount` and `UnloadedClassCount` (`java.lang:type=ClassLoading`), interpreted as
  trends rather than a leak verdict
- Metaspace usage, alerting **before** `MaxMetaspaceSize`
- `jdk.ClassLoaderStatistics` in the continuous JFR recording
- `-Xlog:class+unload=info` during a bounded diagnostic window

## Find the retainer

```bash
jcmd <pid> GC.heap_dump /secure/diagnostics/heap.hprof
```

In Eclipse MAT: _Path to GC Roots_, **excluding weak references**. The usual suspects, in
the order they are usually found:

- a `ThreadLocal` on a pooled thread
- a JDBC driver registered in `DriverManager` from inside the reloadable artefact
- a shutdown hook
- a listener registered on a singleton that outlives the loader
- a reflection cache keyed by `Class`
- a live thread whose context class loader is the obsolete loader
- an executor, timer, `ServiceLoader`, MBean, logging/serialization cache, or native callback
  registered into a parent-owned singleton

A heap dump can pause a large JVM, consume disk comparable to live heap and expose credentials
and customer data. Confirm capacity/access controls and use the repository's incident-evidence
policy before capture. Follow the path from loader to a **parent- or bootstrap-owned root**; a
cycle entirely inside the child is collectible.

## The two-part `close()` trap

```java
// ❌ No deterministic release of opened JAR/file resources
URLClassLoader cl = new URLClassLoader(urls, parent);

// ✅ Closes the JARs...
try (URLClassLoader cl = new URLClassLoader(urls, parent)) { /* ... */ }
```

`close()` releases file handles. It does **not** release Metaspace. If any object created
by the loader remains reachable, the loader remains alive and no class is unloaded. Both
halves are required: close it _and_ leave nothing reachable behind.

## Validate

Repeat the same lifecycle workload and measurements, including unloading events and Metaspace
after a comparable GC opportunity. Validate that obsolete cohorts disappear, file handles close,
and current plugins still function; forcing `System.gc()` is not a production fix.

## Instrumentation agents

An agent without a package filter can transform or cache far more than intended. Bound matching,
prefer weak keys where semantics permit, remove per-loader state during shutdown, and test
retransformation across plugin cycles. A filter reduces risk but does not prove the agent keeps
no `Class`, `Method`, method-handle or transformed-byte cache alive.
