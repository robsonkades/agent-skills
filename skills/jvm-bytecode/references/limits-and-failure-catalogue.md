# Limits, verification flags and the failure catalogue

Every message below was reproduced on Temurin 25.0.3 by patching or transforming a class file
unless the row says otherwise. Match the text first; most of these errors are diagnosed by the
message alone, and the wrong hypothesis (usually "the JVM is broken") costs hours.

## Symptom to cause

| Message                                                                                                                                                                                                       | Cause                                                                                                                                                                                                                         | Next step                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `VerifyError: Expecting a stackmap frame at branch target 12` with `Location: Lab.<clinit>()V @5: ifne` and `Reason: Expected stackmap frame at this location.`                                               | A rewritten body has no valid frame at a required target. A physically absent `StackMapTable` means an implicit empty table for version 50+; version 50 alone had limited failover rules.                                     | Dump the rejected transformed class; compare code, handlers, maximums and frames at the reported BCI. Fix the generator.                       |
| `VerifyError: Bad type on operand stack` with `Location: Lab.constFold()I @4: ireturn` and `Reason: Type null (current frame, stack[0]) is not assignable to integer`                                         | Instructions and frames disagree: an instruction was inserted or replaced with the wrong stack effect, or frames were copied from the original while the code moved.                                                          | Same. `Current Frame:` in the message is the verifier's view at that `bci`; compare it with what the instruction needs.                        |
| `VerifyError: Inconsistent stackmap frames at branch target N` (text from HotSpot `verifier.cpp`; not reproduced here)                                                                                        | Stale frames after an edit — the classic agent bug.                                                                                                                                                                           | `COMPUTE_FRAMES` in ASM, or the Class-File API's default regeneration.                                                                         |
| `UnsupportedClassVersionError: Lab has been compiled by a more recent version of the Java Runtime (class file version 70.0), this version of the Java Runtime only recognizes class file versions up to 69.0` | Build image newer than the runtime image.                                                                                                                                                                                     | Align `--release` with the base image tag. The late-linkage rows hand over to `jvm-class-loading`: which loader defined each class, and
why identically named definitions from different loaders are distinct runtime types.

## Class-file limits

| Limit                       | Value                                                                                                   | JVMS   | javac says            |
| --------------------------- | ------------------------------------------------------------------------------------------------------- | ------ | --------------------- |
| Code per method             | `code_length` < 65536                                                                                   | 4.7.3  | `code too large`      |
| Constant pool               | `constant_pool_count` ≤ 65535; at most 65534 indexed entries, with unusable slots after `long`/`double` | 4.1    | `too many constants`  |
| Parameters                  | ≤ 255 slots, `this` included                                                                            | 4.3.3  | `too many parameters` |
| Fields, methods, interfaces | ≤ 65535 each                                                                                            | 4.1    | —                     |
| `max_locals`, `max_stack`   | ≤ 65535 each                                                                                            | 4.7.3  | —                     |
| Branch offset               | 16-bit; `goto_w` and `jsr_w` carry 32-bit offsets                                                       | 6.5    | rewritten by javac    |
| Bootstrap method arguments  | ≤ 65535 per entry                                                                                       | 4.7.23 | —                     |

The 64 KB limit is per **method**, not per class, and it is why generated code (JSP, template
engines, protobuf builders, mapping code) fails compilation before anything else does. It also
frames the `HugeMethodLimit` problem above: a method can be legal for the class file and still
too large for the JIT.

## Verification flags on JDK 25

| Flag                              | Class                 | Default | Verified behaviour                                                                                                                                               |
| --------------------------------- | --------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-Xverify:none`, `-noverify`      | launcher              | —       | Still accepted; prints `Options -Xverify:none and -noverify were deprecated in JDK 13 and will likely be removed in a future release.` (JDK-8214719)             |
| `-XX:-BytecodeVerificationRemote` | diagnostic            | `true`  | Needs `-XX:+UnlockDiagnosticVMOptions` first; otherwise `VM option 'BytecodeVerificationRemote' is diagnostic`. Verifies everything the boot loader did not load |
| `-XX:+BytecodeVerificationLocal`  | diagnostic            | `false` | Boot-loader classes are **not** verified by default — trusted by construction                                                                                    |
| `-Xlog:verification`              | unified logging       | —       | `Verifying class Lab with new format`, then `Verification for Lab failed` before the `VerifyError`                                                               |
| `-XX:-UseSplitVerifier`           | removed (JDK-8009595) | —       | `Unrecognized VM option 'UseSplitVerifier'` — **the JVM does not start**                                                                                         |
| `-XX:+FailOverToOldVerifier`      | absent from JDK 25    | —       | Not listed by `-XX:+UnlockDiagnosticVMOptions -XX:+PrintFlagsFinal`; the release that removed it is not verified here                                            |

In the tested malformed-class experiment, disabling remote verification suppressed the
stack-map failure. That observation is not a remediation: it removes a structural/type gate
before execution and can change failure into unsafe or implementation-dependent behaviour.
Measure startup separately and use supported caching/AOT mechanisms; fix the generator.
