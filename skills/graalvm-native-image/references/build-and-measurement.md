# Build and measurement recipes

Commands are illustrative. Resolve them through the framework/build plugin and verify options with
the installed `native-image` release before making them CI policy.

## Reproducible build contract

Pin or record:

- GraalVM distribution and full version, framework AOT plugin, Native Build Tools, Maven/Gradle,
  compiler/linker, OS/base image, architecture and libc;
- dependency lock/checksums, reachability metadata source versions, effective Native Image options,
  environment variables that affect the builder, and target `-march`;
- build duration, peak builder RSS/CPU, build report, SBOM, binary hash, symbols, and signing result.

The builder is a JVM and whole-program analysis is memory intensive. In constrained CI, set the
builder heap with `-J-Xmx...` and parallelism with `--parallelism=...` from measurements. Exit 137
usually means the container or host killed the process; it is not a Java exception and increasing
parallelism may worsen it.

## Collect and review reachability metadata

Prefer metadata already generated by the framework or shipped by the library. Use the tracing agent
for application-specific discovery:

```bash
java -agentlib:native-image-agent=config-merge-dir=src/main/resources/META-INF/native-image \
     -jar app.jar
```

Run representative integration scenarios: valid and invalid inputs, every enabled integration,
serialization variants, resources/locales, error handlers, TLS/security providers, JNI/FFM paths,
shutdown, and feature-flag combinations. Multiple targeted runs are easier to review than one opaque
manual session.

Then:

1. diff the generated configuration;
2. remove entries owned by tests or irrelevant callers;
3. replace broad member access with the intended minimum;
4. add conditions for optional types;
5. validate the JSON against the release's shipped schema;
6. build exact mode and execute the native artifact's integration suite.

```bash
native-image --exact-reachability-metadata -jar app.jar -o app
./app -XX:MissingRegistrationReportingMode=Exit
```

For GraalVM 25.1 and later, do not add `--no-fallback`: fallback images were removed and the flag is
deprecated with no effect. On older maintained lines where fallback exists, keep `--no-fallback`
to turn an unsupported build into an explicit failure.

## Inspect initialization and build output

Use supported reports first:

```bash
native-image --emit build-report -jar app.jar -o app
native-image -H:+PrintClassInitialization -jar app.jar -o app
native-image --verbose -jar app.jar -o app
```

Some reports and flags differ by distribution. For expert options, query the installed binary:

```bash
native-image --expert-options
native-image --expert-options-detail=PrintClassInitialization
```

Inspect why each environment-dependent class is build-time initialized. Do not “fix” an error by
moving a package wholesale to build time or runtime; choose the smallest class boundary and retest
startup, image size, and semantics.

## CPU, linking, and portability

```bash
native-image -march=list
native-image -march=compatibility -jar app.jar -o app-portable
native-image -march=native -jar app.jar -o app-local
```

Current AMD64 defaults use `x86-64-v3`; defaults on other architectures and releases can differ.
Use an explicit baseline derived from the oldest fleet CPU. Test the output on that CPU or an
appropriate compatibility runner. `-march=native` is for artifacts deployed only to compatible
machines, not generic CI artifacts.

Choose dynamic glibc, static musl, or another supported target based on DNS/TLS/locale behavior,
debugging, binary compatibility, vulnerability patch strategy, and image size. Static linking can
simplify deployment but requires rebuilding the application to pick up embedded library fixes.

## Collector and heap experiment

```bash
native-image --gc=serial -jar app.jar -o app-serial
native-image --gc=G1 -jar app.jar -o app-g1       # current Oracle GraalVM only

./app-serial -Xmx512m
./app-g1 -Xmx512m -XX:MaxGCPauseMillis=100
```

Use the same memory limit but do not assume identical heap size is automatically fair: collector
headroom and non-heap components differ. Report Java heap, total RSS, transient GC peak, allocation
rate, live set after collection, pause distribution, CPU, and OOM behavior. Leave container
headroom. Avoid Epsilon unless the maximum allocation over the bounded process lifetime is proven
below the memory budget and failure is acceptable.

## Profile-guided optimization

Current JDK 25 Community Edition does not provide PGO. With a supporting Oracle GraalVM release:

```bash
native-image --pgo-instrument -jar app.jar -o app-instrumented
./app-instrumented --profile-output=training.iprof
native-image --pgo=training.iprof -jar app.jar -o app-pgo
```

Treat the profile as training data:

- collect it from the intended traffic mix, including expensive but less frequent branches;
- keep an independent evaluation workload so over-specialization is visible;
- compare PGO and non-PGO from the same source, dependencies, toolchain, flags, and CPU target;
- inspect throughput, tail latency, CPU, size, and correctness—not only a mean score;
- retrain after meaningful hot-code or traffic-shape changes.

There is no portable percentage gain. A profile can provide little benefit or bias optimization
toward the wrong workload.

## Size, symbols, and supply chain

`-Os` optimizes for size; `-Ob` shortens development builds; `-O2` is the normal balanced default
in current releases. `-O3` is not automatically better in every distribution/workload. Measure
binary size, startup, RSS, and performance before selecting an optimization level.

Use `--strip-debug` or split debug symbols according to incident and distribution policy. Keep
symbols in an access-controlled artifact store keyed by the binary build ID/hash. An executable
packer such as UPX reduces on-disk/transferred bytes, not Java heap, and may disrupt signing,
security scanners, page sharing, startup, or crash tools; it is an optional packaging experiment,
not a default Native Image optimization.

Extract or retain the embedded SBOM with the release-supported `native-image-utils` command, scan
the produced artifact and base image, sign/attest it, and record the builder JDK. Rebuild after JDK,
SubstrateVM, compiler, libc, or embedded native-library security updates.

## Fair Native Image versus HotSpot experiment

Define the hypothesis and acceptance thresholds before running either candidate.

| Metric           | Measurement requirement                                                 | Common invalid comparison                         |
| ---------------- | ----------------------------------------------------------------------- | ------------------------------------------------- |
| Startup          | process start to first correct response; distribution over fresh starts | shell `time` around different readiness semantics |
| Idle footprint   | stabilized RSS/PSS after equivalent initialization                      | reserved virtual memory versus RSS                |
| Loaded footprint | RSS/PSS plus heap/live set at the same offered and achieved load        | different heap ceilings or request mix            |
| Throughput       | achieved rate below and at saturation, with errors included             | fixed short duration while HotSpot compiles       |
| Latency          | p50/p95/p99/max and timeout rate at several utilizations                | percentile from coordinated-omission-prone client |
| CPU efficiency   | CPU time per successful operation and throttling                        | host CPU percent without achieved work            |
| Delivery         | build time, peak builder resources, artifact bytes, pull/start time     | ignoring native build and target-matrix cost      |

Control OS/kernel, host shape, CPU frequency policy, container limit, request data, dependency state,
network placement, logging/telemetry, heap policy, and concurrency. Use multiple independent process
forks. For HotSpot, report cold behavior and a separately defined steady state using compilation/JFR
evidence. For Native Image, include first request and steady state; “no JIT warm-up” does not mean
all caches, pools, connections, or application data are already warm.

Increase offered load until the SLO boundary and saturation mechanism are visible. A single
60-second `wrk` result cannot establish fleet economics or tail behavior. Preserve commands, raw
histograms, environment metadata, errors, and uncertainty.

## Release gate

- [ ] Native and JVM acceptance criteria are explicit, including rollback triggers.
- [ ] Dynamic-access and initialization contracts pass on the produced binary.
- [ ] Oldest CPU, target OS/libc, container limit, and shutdown/signal behavior are tested.
- [ ] GC and heap have headroom under peak representative load.
- [ ] Required JFR/`jcmd`/heap-dump/thread-dump/profiler procedures are rehearsed.
- [ ] Build inputs, report, SBOM, symbols, hash, signature, and builder-resource cost are retained.
- [ ] PGO uses representative training data and an independent evaluation workload.
- [ ] Cold and steady-state results include errors and latency distributions, not only averages.
- [ ] JVM fallback artifact and operational rollback remain available through the canary period.
